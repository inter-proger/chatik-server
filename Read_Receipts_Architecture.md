# Прочтение другими участниками («галочки»)

Описывает, как клиент узнаёт, до какого сообщения переписку прочитал каждый другой участник, и показывает статус «прочитано» у сообщений. Реализовано; клиентский контракт — в `docs/api/` ([MemberReadMeta](docs/api/Objects.md#объект-memberreadmeta), [метод и правила клиента](docs/api/methods/Conversations.md#get-conversationsgetmembersreadmeta--прочтение-другими-участниками), [событие `memberRead`](docs/api/websocket/Conversations.md#conversations--memberread--участник-прочитал-переписку)), здесь — обоснования. При расхождении верен `docs/api/`. Опирается на указатель прочтения из [Unread_Messages_Architecture.md](Unread_Messages_Architecture.md): данные уже хранятся в `conversation_members.last_read_message_id`, миграция не нужна.

## Коротко

- Новый метод **`GET /conversations/getMembersReadMeta`** — указатели прочтения остальных участников переписки, массивом объектов **MemberReadMeta**.
- Новое WS-событие **`conversations` / `memberRead`** — участник сдвинул указатель; приходит остальным участникам.
- Клиент запрашивает мету при открытии экрана переписки и после переподключения WS, пока экран открыт. Событиями обновляет мету открытой переписки и уже сохранённую мету других. Мета хранится локально и показывается в оффлайне.
- Сообщение прочитано участником, если `messageId <= lastReadMessageId` этого участника.
- В списке переписок прочтение другими не показывается; `Conversation`, `changeVersion` и курсор синхронизации не меняются.

## Сценарий клиента

1. Пользователь открывает переписку → сразу показывает сохранённую мету (если есть) → вызывает `getMembersReadMeta` → сливает ответ с локальной метой и сохраняет.
2. Событие `memberRead` применяется, если переписка открыта или её мета уже сохранена. Переписки без сохранённой меты событие не создаёт: при открытии мета всё равно запрашивается.
3. Переподключение WS (`auth` / `connected`) при открытом экране переписки → повторный `getMembersReadMeta`: события за время разрыва потеряны, доставка по WS не гарантирована.
4. Корректность держится на запросе при открытии; события вне экрана — уточнение для оффлайн-показа.

### Слияние

Указатель прочтения только растёт ([правила прочтения](Unread_Messages_Architecture.md#правила-прочтения)), поэтому версии не нужны: для каждого участника берётся **максимум** из локального значения, ответа метода и события. Для указателей порядок прихода ответа и событий не важен — гонка «событие пришло раньше ответа на запрос» разрешается сама.

Состав участников берётся из ответа метода: участники, которых в ответе нет, удаляются из локальной меты. Иначе вышедший из группы остался бы в ней навсегда. Событие от участника, которого нет в локальной мете, добавляет его.

Для состава порядок важен, и здесь допускается неточность: если ответ собран до вступления участника, а его `memberRead` пришёл раньше ответа, ответ удалит только что добавленного участника. Это исправит следующее открытие переписки. Слияние по максимуму не переживёт и уменьшения указателя (выход из группы и повторное вступление с меньшим указателем): он исправится, только если между выходом и вступлением клиент получил ответ метода без этого участника. Сейчас групп нет; когда появятся, это пересматривается вместе с [вступлением в группу](#на-будущее).

### Своё сообщение участника

Отправка сообщения сдвигает указатель отправителя на это сообщение (`Message::send`), отдельного события `memberRead` при этом нет: остальные участники и так получают `messages` / `received` с `senderId`. Правило клиента: при получении сообщения от участника X его указатель = `max(указатель X, messageId)` — при том же условии, что и для `memberRead`: переписка открыта или её мета уже сохранена. Метод `getMembersReadMeta` это уже учитывает — сервер хранит сдвинутый указатель.

Следствие: если X ответил, не открывая переписку (например, из уведомления), все сообщения до его ответа показываются прочитанными им. Это прямое продолжение правила «отправка отмечает прочитанной всю переписку до сообщения» и принято сознательно (так же ведёт себя, например, Telegram).

### Статус сообщения

| Переписка | Статус своего сообщения `id` |
| --- | --- |
| `single` | прочитано, если указатель собеседника `>= id` |
| `group` | прочитано кем-то — хотя бы один указатель `>= id`; всеми — минимум указателей `>= id`; «кто прочитал» — участники с указателем `>= id` |

## API

### Объект MemberReadMeta

Указатель прочтения одного участника переписки. Новый раздел в `docs/api/Objects.md`.

| Поле | Тип | Описание |
| --- | --- | --- |
| `userId` | Int | Участник |
| `lastReadMessageId` | Int | Последнее прочитанное сообщение; `0` — ничего не прочитано |

Объект, а не словарь `userId → messageId`: в JSON ключи словаря — строки (`{"2": 15}`), клиентам пришлось бы их разбирать. Объект к тому же расширяем (время прочтения, скрытие настройками приватности).

Имя — `Meta`, а не `Info`: [ReadInfo](docs/api/Objects.md#объект-readinfo) — состояние прочтения текущего пользователя вместе со счётчиками и версией, а здесь только указатель другого участника. Разные имена не дают спутать объекты с разными правилами слияния.

### `GET /conversations/getMembersReadMeta`

| Параметр | Тип | Описание |
| --- | --- | --- |
| `conversationId` | Int | Переписка |

| Поле ответа | Тип | Описание |
| --- | --- | --- |
| `membersReadMeta` | Array of MemberReadMeta | Указатели всех участников, кроме текущего пользователя |

Текущего пользователя в ответе нет: его указатель уже есть в `Conversation.lastReadMessageId` и сливается по `changeVersion`. Второй источник того же значения с другими правилами слияния вёл бы к рассинхрону.

```json
{
  "membersReadMeta": [
    { "userId": 2, "lastReadMessageId": 15 }
  ]
}
```

Ошибки: `5002 CONVERSATION_NOT_FOUND` — нет переписки, некорректный `conversationId` или пользователь не участник. Новых кодов нет.

Action `users` метод не отдаёт: все `userId` в ответе — участники переписки, они уже известны клиенту из `memberIds` переписки и загружены вместе с ней. Повторно проверять их наличие в кэше клиенту не нужно.

Сервер: после проверки участия один `SELECT user_id, last_read_message_id FROM conversation_members WHERE conversation_id = ? AND user_id <> ? ORDER BY user_id`. Транзакция и блокировки не нужны.

### WS: `conversations` / `memberRead`

Сервер → клиент. Приходит во все соединения остальных участников переписки, когда `/conversations/markRead` сдвинул указатель (`$changed`). Если указатель не сдвинулся — события нет. Самому прочитавшему не отправляется: у него есть `conversations` / `read`. Сервер не знает, какой экран открыт у клиента, поэтому рассылает событие всегда; что с ним делать, решает клиент (см. [сценарий](#сценарий-клиента)).

| Поле `body` | Тип | Описание |
| --- | --- | --- |
| `conversationId` | Int | Переписка |
| `userId` | Int | Кто прочитал |
| `lastReadMessageId` | Int | Новый указатель |

`userIds` нет: `userId` — участник переписки, он уже известен клиенту из `memberIds` переписки, повторно проверять его наличие в кэше не нужно.

```json
{
  "uid": "3c5e7a9b-1d2f-4a6c-8e0b-2d4f6a8c0e1b",
  "group": "conversations",
  "event": "memberRead",
  "body": {
    "conversationId": 1,
    "userId": 2,
    "lastReadMessageId": 15
  }
}
```

Событие **не несёт `changeVersion` и не участвует в [курсоре синхронизации](docs/api/WebSocket.md#курсор-синхронизации)**: версия получателя при чужом прочтении не растёт. Это не противоречит [правилу](Unread_Messages_Architecture.md#принятые-решения) «любое изменяемое поле переписки поднимает `change_version`» — указатели других участников не входят в Conversation. В `docs/api/WebSocket.md` это оговаривается рядом с правилом.

Событие также не несёт полного объекта с `updatedAt`, которого [требует синхронизация](docs/api/WebSocket.md#синхронизация). Это третье исключение рядом с перепиской и прочтением: указатели других участников только растут и сливаются по максимуму, версия им не нужна. В `docs/api/WebSocket.md` исключение добавляется в тот же абзац.

Сервер: в `conversations/markRead.php` после коммита публикация `read` заменяется на один `WebSocket::publishEach` с двумя доставками — `read` пользователю и `memberRead` остальным участникам (`WebSocket::delivery($otherMemberIds, 'conversations', 'memberRead', [...])`). Один внутренний HTTP-запрос к WS-серверу вместо двух.

## Принятые решения

| Вопрос | Решение |
| --- | --- |
| Где отдавать прочтение другими | Отдельный метод и событие, не поле в Conversation. Поле (`opponentLastReadMessageId`) поднимало бы `change_version` остальных при каждом прочтении: лишние записи в `users` и `conversation_members`, версия в событии, участие в курсоре. В списке переписок прочтение другими не показывается, поэтому поле не нужно |
| Форма `membersReadMeta` | Массив объектов MemberReadMeta |
| Имя объекта | `MemberReadMeta`, не `…Info`: не путать с ReadInfo (своё состояние со счётчиками и версией) |
| `userIds` в событии, action `users` в методе | Не нужны: все пользователи — участники переписки, известные из её `memberIds` |
| Имя поля указателя | `lastReadMessageId` везде — как в ReadInfo и Conversation |
| Имя события | `conversations` / `memberRead`; не путать с `conversations` / `read` (своё прочтение, другой получатель и тело) |
| Текущий пользователь в ответе | Не включать |
| Слияние | Максимум по каждому участнику; состав участников — из ответа метода, гонка с событием нового участника исправляется следующим открытием |
| События вне экрана переписки | Сервер рассылает всегда; клиент применяет к открытой переписке и к уже сохранённой мете |
| Переподключение WS при открытом экране | Повторный `getMembersReadMeta` |
| Событие при отправке сообщения | Нет: клиент сдвигает указатель отправителя по `messages` / `received` |
| Ответ без открытия переписки | Считается прочтением всего до ответа — следствие правила прочтения при отправке |
| Версия в `memberRead` | Нет; событие вне курсора синхронизации и без полного объекта, оба исключения оговариваются в документации |
| Публикация в `markRead` | `read` и `memberRead` одним `publishEach` |

## На будущее

- **Большие группы.** Каждый `markRead` рассылается N − 1 участникам, а читают все — нагрузка на WS растёт как N². Для личных чатов и небольших групп это незаметно, `markRead` и так с debounce. Для групп на сотни участников — троттлинг на сервере (прочтения переписки за 1–2 с одним событием с массивом, новым событием), рассылка только по последнему сообщению или мета только по запросу.
- **Вступление в группу.** Новому участнику выставлять указатель на `last_message_id` при вступлении. Иначе сообщения до вступления никогда не станут «прочитаны всеми».
- **Приватность.** Отключение отчётов о прочтении (обычно взаимное: не показываю свои — не вижу чужие) — фильтрация на сервере в методе и событии; формат-объект это допускает.
