# ServerAi

PHP REST API без фреймворка: `index.php` — роутер, обработчики методов лежат в каталогах по префиксу URL (`auth/`, `profile/`, `files/`), общий код — в `core/`. WebSocket-сервер — отдельный процесс `websocket/server.php`. Вход в документацию — `README.md` в корне, устройство кода — `docs/architecture/Overview.md`.

## Правила именования

- **API (методы, параметры запросов, поля ответов) — `lowerCamelCase`**: `/files/uploadImage`, `/profile/setAvatar`, `userId`, `fileId`, `errorCode`, `smallUrl`.
- **База данных (таблицы, колонки, ключи внутри JSON-колонок) — `snake_case`**: `users`, `avatar_file_id`, `small_path`.
- Преобразование между ними делается в `fromRow()` сущностей (`core/User.php`, `core/File.php`) — наружу из БД snake_case не протекает.

## Работа с git

- **Каждая задача — в своей ветке, не в `main`.** Перед началом работы проверить текущую ветку: если это `main` — создать ветку под задачу (`feature/<кратко>`) от актуального `main`.
- **Ветка не пустая на момент начала задачи** (есть коммиты, которых нет в `main`, или незакоммиченные изменения) — сообщить об этом до начала работы и предложить на выбор: сначала влить ветку в `main` или создать для новой задачи отдельную ветку.
- **В `main` — только через pull request.** Напрямую в `main` не коммитить и не вливать. После коммита спросить, создавать ли pull request (`gh pr create --base main`).

## Порядок разработки

По умолчанию задача проходит шаги ниже по порядку; пропустить или объединить шаги — только по указанию пользователя. Подробно — `docs/development/Guide.md#порядок-разработки`.

1. **Документ.** Описать планируемые изменения в `docs/architecture/<Функция>.md`: контракт API, модель данных, алгоритмы, граничные случаи, принятые решения, план реализации. По документу самому предложить улучшения, высказать замечания и подсветить решения с плохой практикой; внести корректировки, согласованные с пользователем.
2. **Ревью документа — в отдельной сессии без контекста шага 1** (предложить пользователю новую сессию с fresh-контекстом: что проверить и где документ). Замечания показать пользователю; исправлять только подтверждённые.
3. **Реализация** по документу — код, тесты, документация API в `docs/api/`, миграции. Расхождения с документом — обсудить и отразить в документе.
4. **Ревью реализации — в отдельной сессии без контекста** (изменения ветки относительно `main` и документ из шага 1). Замечания — так же: исправлять после подтверждения.
5. **Проверка локально.** Применить новые миграции к локальной БД (`config/db.php`), прогнать `php tests/run.php`, запустить локальный сервер (`php -S localhost:8080 index.php` и `php websocket/server.php`) и убедиться, что он работает и затронутые методы отвечают корректно.
6. **Документ с изменениями для клиентов** — `docs/api/changes/ГГГГ-ММ-ДД_<Функция>.md` по шаблону из `docs/development/Guide.md#документ-с-изменениями-для-клиентов` и строка в оглавлении `docs/api/Changes.md` (сверху — новые). Пишется для разработчиков клиентов: что изменилось в API и что им сделать, без серверных деталей. Если клиентский контракт не изменился — документ не нужен, сказать об этом пользователю.
7. **Коммит и pull request** — по правилам из «Работа с git».

## Прочее

- Документация — только markdown, в `docs/` по разделам: `api/` — клиентский контракт, `architecture/` — серверное устройство и решения, `operations/` — развёртывание и конфигурация, `development/` — разработка и тесты. Оглавление всего — `README.md` в корне; новый документ добавлять туда (архитектурный — и в таблицу «Документы раздела» в `docs/architecture/Overview.md`).
- Документация API: `docs/api/README.md` — оглавление (`General.md`, `Objects.md`, `Errors.md`, `Methods.md`, `WebSocket.md`, `Admin.md`, `Changes.md` — сводки изменений для клиентов из `docs/api/changes/`); методы — по группам в `docs/api/methods/` (`Global.md`, `Auth.md`, …), `Methods.md` — их оглавление, новый метод добавлять и туда. WS-события — по группам в `docs/api/websocket/` (`Auth.md`, `Messages.md`, …), оглавление — раздел «События» в `WebSocket.md`. При добавлении или изменении метода, объекта, кода ошибки или WS-события обновлять соответствующий документ в том же изменении; ссылки между документами — относительные, `Файл.md#якорь`.
- Изменения схемы БД — отдельным файлом-миграцией в `db/` с порядковым номером (`004_....sql`) и с обновлением `docs/architecture/DataModel.md`. Новая настройка — в `docs/operations/Configuration.md`. Чек-листы изменений — `docs/development/Guide.md`.
- `config/db.php` и `config/app.php` в репозиторий не попадают; шаблоны — `config/db.example.php` и `config/app.example.php`.
- Развёртывание на новом окружении — `docs/operations/Deployment.md`. Новые зависимости (расширения PHP, версии), настройки в шаблонах конфигов, каталоги для записи или процессы — отражать там в том же изменении.
- Тесты: `php tests/run.php [фильтр]` — без зависимостей, нужен локальный MySQL. Раннер пересоздаёт БД `serverai_test` из `db/*.sql` (доступ — `tests/config/db.php`, переопределяется переменными `TEST_DB_*`) и поднимает `php -S` и WebSocket-сервер с тестовым конфигом через `SERVERAI_CONFIG_DIR`. Юнит-тесты сущностей — `tests/unit/`, тесты методов API — `tests/api/`; новый метод или правка метода — вместе с тестами. Подробно — `docs/development/Testing.md`.
