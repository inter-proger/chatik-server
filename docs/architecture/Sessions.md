# Аутентификация и сессии

[← Обзор архитектуры](Overview.md)

Пользователь аутентифицируется стандартной PHP-сессией на файлах: cookie `PHPSESSID` ↔ файл в `storage/sessions/`, в сессии — `user_id`. Клиентский контракт (cookie, время жизни, методы `/auth/*`) — [General.md](../api/General.md) и [methods/Auth.md](../api/methods/Auth.md); здесь — серверная сторона.

Код: `core/Session.php` (старт и продление), `core/Auth.php` (текущий пользователь), `auth/*.php` (регистрация, вход, выход), `core/Admin.php` (админка). Настройки — `config/session.php`.

## Сессия

`Session::start()` перед `session_start()` настраивает:

| Настройка | Значение | Зачем |
|-----------|----------|-------|
| `session.save_path` | `storage/sessions` (`SESSION_DIR`), создаётся с правами `0700` | Свой каталог: сессии не удалит сборщик мусора других PHP-приложений или очистка системного `/tmp` |
| `session.gc_maxlifetime` | `SESSION_LIFETIME` (30 дней) | Файл сессии живёт столько же, сколько cookie |
| `session.use_strict_mode` | `1` | Неизвестный id из cookie не принимается — PHP выдаёт новый. Защита от навязывания id сессии |
| cookie | `lifetime` 30 дней, `path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` — если `BASE_URL` начинается с `https://` | Локально по `http` cookie работает без `Secure` |

**Продление.** Срок — 30 дней с последнего запроса, требующего авторизации. PHP переотправляет cookie только при создании сессии, поэтому для существующей `Session::start()` сам вызывает `setcookie()` с новым сроком; файл сессии получает новый `mtime` за счёт `session.lazy_write` (touch без изменения данных).

**Очистка.** Сборщик мусора PHP в Debian/Ubuntu выключен (`session.gc_probability = 0`), а системный cron чистит только свой каталог — старые файлы в `storage/sessions` удаляет cron проекта ([Deployment.md](../operations/Deployment.md#10-обслуживание)).

**Блокировка.** Файловые сессии блокируют файл на всё время запроса (`session_write_close()` в коде не вызывается), поэтому параллельные запросы одного клиента с одной cookie выполняются по очереди. Методы короткие, и это не мешает; если появится долгий метод, ему стоит закрывать сессию сразу после проверки авторизации.

**Данные сессии:** `user_id` (int) и `name` пользователя; у сессии админа — `is_admin`.

## Текущий пользователь

- `Auth::requireUserId()` — для методов, требующих авторизации: стартует сессию (и продлевает её), без пользователя отвечает `2003` (`NOT_AUTHENTICATED`) и завершает запрос.
- `Auth::currentUserId()` — для методов, доступных и анониму (`/global/start`): возвращает `null`, а если cookie сессии нет вовсе — даже не стартует сессию, чтобы не создавать пустые файлы для анонимов.

Оба на каждый запрос проверяют, что пользователь из сессии существует (`SELECT 1 FROM users`). Если его удалили, данные сессии сбрасываются и запрос считается неавторизованным.

## Регистрация и вход

**`/auth/signup`:**

- проверки (все строки предварительно обрезаются по краям):
  - `login` — `^\w+$` (латиница, цифры, `_`), не длиннее 64 байт → иначе `1001`;
  - пароль — от 8 символов, есть заглавная и строчная латинская буква и цифра → иначе `1002`;
  - `name` — буквы любого алфавита, цифры, `-`, `_`, пробел, до 128 символов → иначе `1003`;
- пароль хешируется `password_hash(…, PASSWORD_BCRYPT)`;
- занятость логина не проверяется заранее: вставка ловит ошибку уникального ключа `1062` и отвечает `2001` — так нет гонки между проверкой и вставкой;
- после регистрации пользователь сразу входит (как при `/auth/login`).

**`/auth/login`:** проверки мягче — `login` по тому же шаблону, пароль — не короче 6 символов (`1002`); остальные требования к паролю при входе не проверяются. Неизвестный логин и неверный пароль дают один и тот же `2002`.

**Смена сессии при входе.** И signup, и login вызывают `session_regenerate_id(true)`: id сессии меняется, старый файл удаляется (защита от фиксации сессии). Если старая сессия уже была авторизована (вход под другим пользователем в том же клиенте), её WebSocket-токены отзываются, а WS-соединения закрываются с кодом `4003` — `WebSocket::endSession()`.

**`/auth/logout`:** только для авторизованной сессии (иначе `2003`). `WebSocket::endSession()` для текущей сессии, очистка `$_SESSION`, просроченная cookie, `session_destroy()`. Другие сессии пользователя (другие устройства) не затрагиваются.

## Связь с WebSocket

WS-сервер PHP-сессии не читает. Доступ к нему даёт одноразовый токен, который выдаётся авторизованной сессии и привязан к её id (`websocket_tokens.session_id`). Поэтому выход и смена сессии отзывают токены по id сессии и закрывают соединения этой сессии — [WebSocket.md](WebSocket.md#токены-подключения).

## Админ-панель

Сессия админа — та же `Session::start()` (тот же каталог и срок жизни), но с другим именем cookie: `ADMINSESSID` (`Admin::SESSION_NAME`). Сессии пользователя и админа не пересекаются: вход в админку не даёт доступа к пользовательским методам, и наоборот.

- `/admin/login` сверяет логин и пароль через `hash_equals()`, причём обе проверки выполняются всегда — время ответа не выдаёт, совпал ли логин. Затем `session_regenerate_id(true)` и `$_SESSION['is_admin'] = true`.
- `Admin::require()` в каждом методе админки: без cookie `ADMINSESSID` или без `is_admin` в сессии — `2003`.
- **Учётные данные захардкожены** в `core/Admin.php` (`admin` / `admin`) — до выноса в `config/app.php` на открытом сервере их нужно сменить или закрыть `/admin` по IP ([Deployment.md](../operations/Deployment.md#безопасность--перед-открытием-наружу)).
