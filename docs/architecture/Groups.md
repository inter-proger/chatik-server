# Групповые чаты

[← Обзор архитектуры](Overview.md)

Описывает первую итерацию групповых переписок (`type: "group"`): создание, состав участников, владельца и выход. Статус — **реализовано**; отличия от исходной постановки — в [отдельном разделе](#отличия-от-исходной-постановки). Клиентский контракт — в `docs/api/` ([методы](../api/methods/Groups.md), [события](../api/websocket/Groups.md), [GroupInfo](../api/Objects.md#объект-groupinfo)), здесь — устройство и обоснования. При расхождении верен `docs/api/`.

Опирается на [UnreadMessages.md](UnreadMessages.md) (версия пользователя, `changedAfter`), [ConversationList.md](ConversationList.md) (позиция в списке), [ReadReceipts.md](ReadReceipts.md) (указатели других участников, схема «запрос при открытии + события») и [Files.md](Files.md) (загрузка аватара).

## Коротко

- Группа — переписка `type: "group"` с названием `name`, необязательными описанием `description` и аватаром `avatar`. Название, описание и аватар в этой итерации задаются только при создании.
- До **100 участников**. Создатель вступает автоматически и становится **владельцем**; владелец ровно один.
- Владелец может всё: добавлять и удалять участников, передавать владение. Остальные участники читают и пишут сообщения и могут выйти.
- Вся история группы видна любому участнику, в том числе сообщения до его вступления. Сообщения удалённого или вышедшего участника остаются в группе.
- **Состав и роли — отдельная сущность GroupInfo**, не часть Conversation. Она запрашивается при открытии группы (`/groups/getInfo`) и обновляется событиями, как мета прочтения. В Conversation группы `memberIds = null`.
- Изменение состава и владельца **не меняет Conversation остальных участников**: их `updatedInfoAt` и `changeVersion` не растут, они получают событие с новой GroupInfo вне курсора синхронизации. Версия растёт только у добавленных и удалённых — у них меняется список чатов.
- Добавленный узнаёт о группе событием с `conversationId` и своей версией и загружает её через `/conversations/getBatch`. Удалённый — событием с меткой удаления, после оффлайна — из `removedConversations` в ответе `getList` с `changedAfter`.
- Новые методы `/groups/create`, `/groups/addMembers`, `/groups/removeMembers`, `/groups/changeOwner`, `/groups/getInfo`, `/groups/leave` и WS-группа событий `groups`.
- Правило протокола «событие несёт полный объект» заменяется правилом «событие несёт версию и достаточно данных для идемпотентного применения» — см. [правило протокола](#правило-протокола-для-событий).

## Модель данных

Миграция `014_groups.sql`.

### `conversations`

| Колонка | Изменение | Описание |
|---------|-----------|----------|
| `name` | VARCHAR(255) → VARCHAR(128) | Название группы; для `single` — `NULL`. Колонка и поле API не переименовываются — название, как и у пользователя (`User.name`) |
| `description` | новая, VARCHAR(1024) NULL | Описание группы; `NULL` — нет. Для `single` — `NULL` |
| `owner_id` | новая, INT UNSIGNED NULL → `users.id` ON DELETE SET NULL | Владелец группы; для `single` — `NULL`. `NULL` у группы — участников не осталось (или владелец удалён вместе с пользователем; методов удаления пользователей нет) |
| `group_info_version` | новая, INT UNSIGNED NOT NULL DEFAULT 0 | Версия [GroupInfo](#объект-groupinfo): +1 при каждом изменении состава или владельца, под блокировкой строки переписки. У созданной группы — 1; у `single` всегда 0 |
| `avatar_file_id` | без изменений | Аватар группы |

Владелец хранится колонкой в `conversations`, а не ролью в `conversation_members`: владелец ровно один, и колонка гарантирует это без дополнительных проверок. Роль участника в API (`owner` / `member`) вычисляется из `owner_id`. Когда появятся модераторы, роль станет колонкой участника, а `owner_id` останется.

Версия GroupInfo — отдельный счётчик группы, а не версия пользователя: GroupInfo одна на всех участников, и её изменение не должно писать N строк `users` и `conversation_members`.

### `conversation_members`

| Колонка | Изменение | Описание |
|---------|-----------|----------|
| `created_at` | `DATETIME(3) NULL` → `NOT NULL DEFAULT CURRENT_TIMESTAMP(3)` | Время вступления. Пустые значения заполняются `COALESCE(conversations.created_at, conversations.position_updated_at)` (см. [позицию](#позиция-в-списке)) |
| `joined_after_message_id` | новая, INT UNSIGNED NOT NULL DEFAULT 0 | `last_message_id` переписки на момент вступления; не меняется. Сообщения с большим id отправлены после вступления — по ним считается [статус прочтения](#прочтение-для-нового-участника). Существующим строкам — 0 (создатели и участники личных переписок вступили до всех сообщений) |

`created_at` строки участника получает смысл **времени вступления** — на него опирается [позиция в списке](#позиция-в-списке). При удалении и выходе строка удаляется: существующие проверки участия (`Conversation::isMember()`, `JOIN conversation_members` в выборках, рассылка и счётчики в `Message::send()`) остаются верными по смыслу, но изменяющим методам нужна повторная [проверка под блокировкой](#проверка-участия-под-блокировкой) — состав теперь может измениться между проверкой и транзакцией.

### `conversation_removed_members` — метки удаления

Новая таблица: пользователь перестал быть участником, и клиент должен узнать об этом при синхронизации `changedAfter`. Без неё вышедший не попадёт в выборку изменений — его строки участника больше нет (риск отмечен в [UnreadMessages.md](UnreadMessages.md#граничные-случаи-и-риски)).

| Колонка | Тип | Описание |
|---------|-----|----------|
| `conversation_id`, `user_id` | PK (пара), → CASCADE | |
| `change_version` | INT UNSIGNED | `users.change_version` пользователя на момент удаления — та же шкала, что `conversation_members.change_version`. Ключ `(user_id, change_version)` |
| `created_at` | DATETIME(3) | |

Строка создаётся при удалении и выходе, удаляется при повторном добавлении (в той же транзакции, что и вставка в `conversation_members`). Поэтому пара (переписка, пользователь) всегда в одном из двух мест или ни в одном. Метки не чистятся: строка на пару, объём ограничен числом выходов. Чистку старых меток (с запросом полной перезагрузки списка у клиентов с очень старым курсором) можно добавить позже.

Инвариант к [таблице инвариантов](DataModel.md#денормализованные-поля-и-инварианты): ненулевые `change_version` одного пользователя не повторяются по объединению `conversation_members` и `conversation_removed_members`.

## Позиция в списке

Сейчас `positionUpdatedAt` — общий для всех участников `created_at` последнего сообщения. Добавленный в группу без новых сообщений получил бы её со старой позицией: группа оказалась бы где-то в глубине списка, а после оффлайна её не нашла бы и синхронизация — `positionUpdatedAfter` её не вернёт, а `changedAfter` новые переписки в список [не добавляет](../api/methods/Conversations.md#синхронизация-списка).

Решение: **`positionUpdatedAt` группы становится зависимым от смотрящего** — время последнего сообщения или время вступления, что позже. Добавленный видит группу наверху списка, у остальных позиция не меняется. Выражение — только для групп:

```sql
IF(c.type = 'group', GREATEST(c.position_updated_at, m.created_at), c.position_updated_at)
```

- **Личные переписки** не меняются вовсе: у строк участников, созданных до миграции `014`, `created_at` может быть на миллисекунды позже `position_updated_at` (они вставлялись отдельным запросом) — без условия по типу `positionUpdatedAt` личной переписки без сообщений перестал бы совпадать со временем создания (`updatedInfoAt`). Новые строки создателей (личных переписок и групп) получают `created_at` = `conversations.created_at` явно.
- **`NULL`.** `conversation_members.created_at` сейчас `DATETIME(3) NULL` (миграции `004`, `010`), а `GREATEST(x, NULL)` = `NULL`. Миграция `014` заполняет пустые значения временем создания переписки и делает колонку `NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`. Кроме того, `findById()` присоединяет строку смотрящего через `LEFT JOIN` (смотрящий может быть не участником), поэтому в выражении — `COALESCE(m.created_at, c.position_updated_at)`.
- Сортировка `getList` и фильтр `positionUpdatedAfter` — по этому выражению. Индексом сортировка и сейчас не пользуется (сортируются переписки пользователя после `JOIN`), так что план запроса не ухудшается.
- Правило слияния позиции (пара `(positionUpdatedAt, lastMessage.messageId)`) остаётся монотонным для каждого смотрящего: новое сообщение всегда позже вступления.
- События `messages` по-прежнему несут `positionUpdatedAt = message.createdAt` — оно не меньше времени вступления получателя.
- Повторное добавление после удаления — новая строка участника и новое время вступления: группа снова поднимается у вернувшегося.

Когда появятся системные сообщения о вступлении, позиция будет подниматься ими и выражение станет избыточным, но не неверным.

Альтернатива — поднимать общую `position_updated_at` переписки при добавлении участников — отвергнута: группа поднималась бы у всех без видимой причины, и ломается инвариант «позиция = время последнего сообщения».

## Прочтение для нового участника

Новому участнику указатель прочтения ставится на `last_message_id` переписки, `unread_count = 0`: вся история видна, но непрочитанной не считается. Иначе вступление в группу с тысячами сообщений давало бы тысячи непрочитанных. При повторном вступлении указатель не меньше прежнего — слияние меты по максимуму остаётся верным.

Но указатель нового участника не значит, что он прочитал сообщения до вступления. Если считать статус только по указателям ([ReadReceipts.md](ReadReceipts.md#статус-сообщения): в группе «прочитано кем-то» — хотя бы один указатель `>= id`), то добавление участника сразу показывало бы отправителю последних сообщений «прочитано», а новый участник попадал бы в «кто прочитал». Поэтому при вступлении сохраняется ещё и `conversation_members.joined_after_message_id` — тот же `last_message_id` на момент вступления, но, в отличие от указателя, не меняющийся. В [GroupMember](#объект-groupmember) он отдаётся как `joinedAfterMessageId`, и статус в группе считается только по участникам, вступившим **до** сообщения. По id, а не по времени вступления: сообщение и вступление в одну миллисекунду по времени не различить, а id сообщений внутри переписки растут строго и пишутся под той же блокировкой переписки.

- «прочитано кем-то» и «кто прочитал» сообщение M — участники с `joinedAfterMessageId < M.messageId` и указателем `>= M.messageId`;
- «прочитано всеми» — минимум указателей тех же участников `>= M.messageId`; сообщения до вступления новичка этот минимум не задерживает (его указатель и так не меньше), так что проблема из [ReadReceipts.md](ReadReceipts.md#на-будущее) решается.

Мета прочтения хранится по `userId`, а состав — в GroupInfo: участников, которых нет в текущей GroupInfo (удалённых и вышедших), клиент в статусе не учитывает и при новой GroupInfo убирает из локальной меты. Иначе удалённый с отстающим указателем навсегда задержал бы «прочитано всеми» до перезапроса меты.

Удаление и выход вычитают `unread_count` участника из его `users.total_unread_count` (через `GREATEST(…, 0)`); новый общий счётчик приходит удалённому в ответе и событии.

## Правило протокола для событий

Сейчас [синхронизация](../api/WebSocket.md#синхронизация) требует, чтобы событие несло полный объект с `updatedAt`, и перечисляет исключения. Требование заменяется общим правилом — смысл прежнего правила был не в полноте объекта, а в идемпотентности и независимости от порядка доставки (доставка по WS не упорядочена: события параллельных запросов уходят разными вызовами WS-сервера):

> Событие несёт версию изменения и позволяет клиенту применить его идемпотентно и независимо от порядка доставки. Допустимые формы:
> 1. **Полный объект или его независимо версионируемая часть** — клиент сливает по версии (Message по `updatedAt`, GroupInfo по `version`, ReadInfo по `changeVersion`).
> 2. **Ссылка и версия** — клиент перезапрашивает объект по REST (`groups` / `membersAdded` для добавленного: `conversationId` + `changeVersion` → `getBatch`). Версия из такого события считается увиденной (попадает в курсор) **только после успешного ответа REST**: до этого изменение клиенту не известно. Пока запрос не удался, клиент хранит ссылку в списке ожидающих и повторяет запрос после каждого переподключения.
>
> Дельта без версии недопустима: например, `добавлен 5` и `удалён 5`, пришедшие в обратном порядке, оставили бы 5 в группе. Исключение — значения, которые только растут и сливаются по максимуму (указатель в `memberRead`).
>
> У каждой сущности, которую меняет событие, должен быть **путь восстановления после потерянного события** — одно из двух:
> - **синхронизация по курсору** — изменение поднимает версию пользователя, и `getList` с `changedAfter` его вернёт (Conversation, ReadInfo, RemovedConversation);
> - **перезапрос при открытии и после переподключения** — сущность нужна только на открытом экране, клиент запрашивает её при открытии и после каждого `auth` / `connected`, пока экран открыт; сохранённая копия закрытого экрана может устареть до следующего открытия (MemberReadMeta, GroupInfo).
>
> Событие о сущности без такого пути в протокол не добавляется.

Третья форма — дельта с последовательной версией (применять, только если версия равна локальной + 1) — не вводится: ни одно событие ею не пользуется, а потерянная дельта всё равно требует перезапроса. Если понадобится, её добавят вместе с первым событием.

Второе правило — про `changeVersion` и [курсор синхронизации](../api/WebSocket.md#курсор-синхронизации) — не меняется: событие, поднимающее версию пользователя, обязано её нести.

## API

### Объект Conversation

| Поле | Изменение |
|------|-----------|
| `name` | без изменений: String \| null. Название группы; для `single` — `null` |
| `description` | новое, String \| null. Описание группы; для `single` и группы без описания — `null` |
| `memberIds` | Int[] → **Int[] \| null**: для `single` — оба участника, как сейчас; для `group` — `null`, состав — в [GroupInfo](#объект-groupinfo). Реальных клиентов пока нет, смена типа никого не ломает |
| `positionUpdatedAt` | смысл уточняется: время последнего сообщения или время вступления текущего пользователя в переписку, что позже (см. [позицию](#позиция-в-списке)) |

Состав в Conversation группы не входит, чтобы его изменение не меняло версию переписки у всех участников, а список чатов не нёс до 100 id на группу (и action `users` на `getList` не тянул сотни пользователей). Число участников в Conversation тоже не кладётся по той же причине — его показывают по GroupInfo на экране группы.

`name`, `description`, `avatar` — информация о переписке, сливаются по правилу 3 ([информация](../api/WebSocket.md#слияние-переписки)) вместе с `updatedInfoAt`: в перечень полей правила 3 в `WebSocket.md` добавляется `description` (`memberIds` там уже есть — для группы приходит `null`). Их изменение (следующая итерация) поднимает `updatedInfoAt` и `changeVersion` всех участников, как сейчас.

### Объект LastMessage

| Поле | Изменение |
|------|-----------|
| `senderId` | новое, Int. Отправитель — для подписи превью в списке групп («Иван: привет»). Отдаётся для всех типов переписок |

Без него клиенту групп нечем подписать превью: состава в Conversation нет, а LastMessage — единственное, что о сообщении есть в списке. Отправитель попадает в action `users` методов, отдающих Conversation (`getList`, `getBatch`, `createSingle`, `/groups/create`).

### Объект GroupInfo

Состав и роли группы. Отдаётся методами `/groups/*` и событиями группы `groups`.

| Поле | Тип | Описание |
|------|-----|----------|
| `conversationId` | Int | Группа |
| `version` | Int | Версия GroupInfo: растёт при каждом изменении состава или владельца. Своя у каждой группы, не связана с версией пользователя |
| `members` | GroupMember[] | Все участники, включая владельца, по возрастанию `userId` |

### Объект GroupMember

| Поле | Тип | Описание |
|------|-----|----------|
| `userId` | Int | Участник |
| `role` | String | `owner` — владелец (ровно один), `member` — участник. Список будет расширяться (модераторы); неизвестную роль клиент показывает как `member` |
| `joinedAfterMessageId` | Int | Последнее сообщение группы на момент вступления участника (`0` — вступил до первого сообщения). Сообщения с большим `messageId` отправлены после его вступления — только по ним участник учитывается в статусе «прочитано» (см. [прочтение для нового участника](#прочтение-для-нового-участника)) |

Массив объектов с ролью, а не `ownerId` + `memberIds`: при появлении модераторов формат не меняется, и у участника уже есть данные о вступлении — тот же довод, что за объект в [MemberReadMeta](ReadReceipts.md#объект-memberreadmeta).

```json
{
  "conversationId": 12,
  "version": 4,
  "members": [
    { "userId": 1, "role": "owner", "joinedAfterMessageId": 0 },
    { "userId": 2, "role": "member", "joinedAfterMessageId": 0 },
    { "userId": 5, "role": "member", "joinedAfterMessageId": 318 }
  ]
}
```

### Правила клиента для GroupInfo

По образцу [меты прочтения](../api/methods/Conversations.md#правила-клиента):

- **Когда запрашивать.** При открытии экрана группы — сначала показать сохранённую GroupInfo, если есть, затем `/groups/getInfo`; после каждого переподключения WebSocket, пока экран открыт. GroupInfo хранится локально и показывается в оффлайне.
- **Слияние.** Пришедшая GroupInfo (ответ или событие) заменяет локальную целиком, если её `version` больше локальной. Порядок прихода не важен.
- **События.** GroupInfo из событий применяется, если группа открыта или её GroupInfo уже сохранена; для других групп событие GroupInfo не создаёт.
- **Права.** Кнопки владельца и предупреждения при выходе клиент показывает по GroupInfo. Окончательно права проверяет сервер (`5004`).
- **Предупреждение при выходе.** Владельцу — что владелец будет назначен автоматически; единственному участнику — что в группе никого не останется и переписка станет недоступна.

Сохранённая GroupInfo закрытой группы может устареть за время разрыва — это исправит запрос при следующем открытии.

### Объект RemovedConversation

Метка: текущий пользователь перестал быть участником переписки.

| Поле | Тип | Описание |
|------|-----|----------|
| `conversationId` | Int | Переписка |
| `changeVersion` | Int | Версия пользователя, на которой он перестал быть участником |

Правила клиента:

- **Применение.** Если переписка загружена и её локальный `changeVersion` меньше пришедшего — клиент удаляет её из списка и её локальный кэш (сообщения, мету прочтения, GroupInfo, ссылку в `pendingConversationIds`). Если пришедшая версия меньше локальной — пользователя уже добавили обратно, метка устарела и игнорируется (на сервере в этом случае метки уже нет, но событие могло прийти с опозданием).
- **Локальная метка.** Применённую метку клиент сохраняет — `removedVersions[conversationId] = changeVersion`, **в том числе по незагруженной переписке**. Любая пришедшая версия этой переписки (ответы `getList`, `getBatch`, события) с `changeVersion` не больше метки отбрасывается; версия больше — повторное добавление: переписка принимается, метка снимается. Без этого ответ REST, снятый до удаления и пришедший после события удаления (например, `getBatch` после `membersAdded` или `getList` с `positionUpdatedAfter`), вернул бы в список «призрак» — переписку, любое действие в которой отвечает `5002`. Метки хранятся вместе со списком переписок и сбрасываются вместе с ним (полная перезагрузка списка, выход из аккаунта).
- **Пропущенное удаление.** Если метод по известной клиенту группе ответил `5002` (`/groups/getInfo`, `messages/getList`, `messages/send`, `conversations/markRead`, `getMembersReadMeta`) или `6002` (`messages/getBlock`), клиент запрашивает её через `/conversations/getBatch`. Переписка в `notFoundIds` — пользователь больше не участник: клиент применяет удаление с меткой на локальной версии переписки (`removedVersions[conversationId]` = её локальный `changeVersion`) и не ждёт синхронизации — настоящая метка с большей версией придёт через `removedConversations` и только сдвинет курсор.

Action `users` — `[создатель]`. Проверка файла — как в `/profile/setAvatar`: файл существует и принадлежит текущему пользователю (`3004`), иначе чужой `fileId` можно было бы перебором подставить в свою группу; тип `image` (`3003`).

### `POST /groups/addMembers` — добавление участников

Только владелец.

| Параметр | Тип | Обязательное | Описание |
|----------|-----|--------------|----------|
| `conversationId` | Int | Да | Группа |
| `userIds` | Int[] | Да | От 1 до 100 пользователей; через запятую или массивом, как `ids` в `getBatch` (`Request::requireIdList()`). Повторы игнорируются |

| Поле ответа | Тип | Описание |
|-------------|-----|----------|
| `addedUserIds` | Int[] | Добавленные, в порядке `userIds` |
| `notAddedUsersInfo` | UserErrorInfo[] | Не добавленные и причина, в порядке `userIds` |
| `groupInfo` | GroupInfo | Состав после изменения. Клиенту владельца не нужно ждать события |

Пользователи обрабатываются по порядку `userIds`. Коды в `notAddedUsersInfo`:

| Код | Причина |
|-----|---------|
| `4001` | Пользователь не найден |
| `5006` | Уже участник (в том числе сам владелец) |
| `5005` | Достигнут лимит 100 участников: добавлены первые по порядку, на остальных — этот код |

Частичный результат — успех (`status: 1`), даже если не добавлен никто; тогда событий нет и версия GroupInfo не меняется. Action `users` — добавленные (остальных участников клиент владельца уже знает по открытой группе).

Событие: `groups` / `membersAdded` всем участникам после изменения — старым и добавленным, с разным телом.

Ошибки: `2003`, `1004` (`userIds` пуст, больше 100 или содержит не id), `5002` (группы нет или текущий пользователь не участник), `5003` (переписка не группа), `5004` (текущий пользователь не владелец).

| `removedUserIds` | Int[] | Удалённые, в порядке `userIds` |
| `notRemovedUsersInfo` | UserErrorInfo[] | Не удалённые: `5007` — не участник (в том числе несуществующий пользователь), `5008` — сам владелец (выйти — через `/groups/leave`) |
| `groupInfo` | GroupInfo | Состав после изменения |

Сообщения удалённых остаются в группе и видны участникам; их авторов клиент загружает через `/users/getBatch` как обычно (`messages` отдают `senderId`).

Событие: `groups` / `membersRemoved` оставшимся и удалённым.

Ошибки: как у `addMembers`.

| Поле ответа | Тип | Описание |

### `POST /groups/leave` — выход из группы

Любой участник, включая владельца.

| Параметр | Тип | Описание |
|----------|-----|----------|
| `conversationId` | Int | Группа |

| Поле ответа | Тип | Описание |
|-------------|-----|----------|
| `removedConversation` | RemovedConversation | Метка выхода с новой версией пользователя |
| `totalUnreadCount` | Int | Общий счётчик после вычета непрочитанных группы, на версии `removedConversation.changeVersion` (сливается по правилам [ReadInfo](../api/Objects.md#объект-readinfo)) |

Если выходит владелец, новым владельцем становится участник с самым ранним вступлением (`conversation_members.created_at`, при равенстве — меньший `userId`): детерминированно — предсказуемо для пользователей и проверяемо тестами. Если выходит последний участник, группа остаётся в БД без участников и с `owner_id = NULL`: сообщения сохраняются, но доступ к ним больше ни у кого нет. Группа не удаляется — данные не теряются безвозвратно, удаление пустых групп при необходимости — отдельной задачей.

Событие: `groups` / `memberLeft` оставшимся и вышедшему.

Ошибки: `2003`, `5002`, `5003`.

### `GET /conversations/getList` — изменение

В режиме `changedAfter` в ответ добавляется поле `removedConversations` — массив [RemovedConversation](#объект-removedconversation) с `changeVersion > changedAfter`. В остальных режимах — пустой массив (поле есть всегда, клиенту не нужна проверка на отсутствие).

- Страница `changedAfter` — `count` записей из объединения строк участника и меток удаления по возрастанию `changeVersion`. `conversations` и `removedConversations` — две части одной страницы; `hasNext` — по объединению.
- Следующая страница — `changedAfter` = максимальный `changeVersion` из обеих частей.
- Метки применяются по правилам [RemovedConversation](#объект-removedconversation): удаляют только **загруженные** переписки — как и остальные результаты `changedAfter`, — но локальная метка сохраняется для любой.

Сервер: `findChangedByMember()` — `UNION ALL` двух выборок по ключам `(user_id, change_version)` с общим `ORDER BY change_version LIMIT count + 1`, затем полные Conversation для участнических строк одним запросом.

### Прочтение другими участниками в группах

[ReadReceipts.md](ReadReceipts.md) опирается на то, что все участники известны клиенту из `memberIds` переписки, поэтому `getMembersReadMeta` не отдаёт action `users`, а `memberRead` — `userIds`. Для групп это больше не так. Изменения (обратно совместимые):

- `/conversations/getMembersReadMeta` отдаёт action `users` с участниками из ответа;
- `conversations` / `memberRead` несёт `userIds: [userId]`.

Клиент и так запрашивает мету и GroupInfo при открытии группы; `memberRead` от только что добавленного участника, которого нет в локальной GroupInfo, загрузит пользователя по `userIds`. Статус «прочитано» в группе клиент считает по мете **и** GroupInfo: только участники из текущей GroupInfo и только по сообщениям после их `joinedAfterMessageId` ([прочтение для нового участника](#прочтение-для-нового-участника)); `memberRead` от пользователя, которого нет в GroupInfo, в статусе не учитывается, пока GroupInfo с ним не придёт. В ReadReceipts.md (таблица «Статус сообщения», «На будущее») и в API (правила клиента `getMembersReadMeta`) обновляются соответствующие обоснования и раздел «Принятые решения».

### Общие правила методов `/groups/*`

- Порядок проверок: авторизация → параметры (`1003`, `1004`, `1007`) → переписка существует и текущий пользователь участник (`5002`) → тип `group` (`5003`) → права владельца (`5004`). Чужая группа неотличима от несуществующей, как и в остальных методах переписок.
- Методы `messages/*` и `conversations/*` работают с группами по участию, контракт не меняется. Удалённый теряет доступ сразу: `messages/send`, `messages/getList`, `conversations/markRead` и `conversations/getMembersReadMeta` отвечают `5002`, `messages/getBlock` — `6002`, `messages/edit` своего старого сообщения — `6001`, `messages/getBlockBatch` и `conversations/getBatch` — `notFoundIds`. Изменяющим методам для этого нужна [проверка участия под блокировкой](#проверка-участия-под-блокировкой).
- `/conversations/createSingle` и логика `single` не меняются.

## WebSocket: группа `groups`

Рассылка — `WebSocket::publishEach()`: отдельные доставки разным группам получателей (у добавленного и удалённого своё тело и своя версия), одним внутренним запросом к WS-серверу. Верхнеуровневое поле `userIds` — только пользователи, которых изменение касается (добавленные, удалённые, вышедший, новый владелец), а не весь состав: событие по закрытой группе не должно заставлять клиента грузить 100 пользователей. Это сужение общего определения `userIds` («пользователи, фигурирующие в событии», [формат сообщений](../api/WebSocket.md#формат-сообщений)): в `WebSocket.md` определение дополняется оговоркой, что событие может перечислять только существенных для него пользователей, а остальных из тела (участников в `groupInfo`) клиент загружает, когда показывает, — как после `/groups/getInfo` по action `users`.

Что несёт событие разным получателям:

| Получатель | Данные | Версия пользователя |
|------------|--------|---------------------|
| Создатель (`created`) | Conversation и GroupInfo | `conversation.changeVersion` — в курсор |
| Добавленный | `conversationId`, `changeVersion`, GroupInfo → клиент загружает Conversation через `getBatch` | `changeVersion` — в курсор |
| Удалённый или вышедший | RemovedConversation и `totalUnreadCount` | `removedConversation.changeVersion` — в курсор |
| Остальные участники | GroupInfo | нет: Conversation не меняется, событие вне курсора, как `memberRead` |

### `groups` / `created`

Во все соединения создателя.

| Поле `body` | Тип | Описание |
|-------------|-----|----------|
| `conversation` | Conversation | Созданная группа |
| `groupInfo` | GroupInfo | Создатель — `owner` |

`userIds` — `[создатель]`. Полный Conversation здесь, а не ссылка, как у добавленного: получатель — сам создатель, объект уже собран для ответа метода, лишний `getBatch` не нужен; по смыслу — аналог `conversations` / `singleCreated`.

### `groups` / `membersAdded`

Всем участникам после изменения — старым и добавленным.

| Поле `body` | Тип | Описание |
|-------------|-----|----------|
| `conversationId` | Int | Группа |
| `addedUserIds` | Int[] | Добавленные |
| `groupInfo` | GroupInfo | Состав после изменения |
| `changeVersion` | Int \| null | Добавленному — его новая версия (для курсора); остальным — `null` |

`userIds` — `addedUserIds`.

Добавленный: `/conversations/getBatch` по `conversationId`, вставка группы в список по позиции (у него — время вступления, то есть наверх) и только затем версия `changeVersion` — в курсор по правилу непрерывности ([форма 2](#правило-протокола-для-событий)). GroupInfo из события он сохраняет сразу.

Если `getBatch` не удался (оффлайн), клиент запоминает `conversationId` в списке ожидающих (`pendingConversationIds`, хранится локально) и повторяет `getBatch` после каждого переподключения, вместе с синхронизацией списка. Пока запрос не удался, версия в `seenVersions` не попадает и курсор на ней останавливается; синхронизация `changedAfter` переставит курсор на версию ответа, но группу в список не добавит — её доставит именно повтор из списка ожидающих. Полагаться на `positionUpdatedAfter` нельзя: пока запрос не удался, `maxPositionUpdatedAt` может уйти вперёд по событиям других переписок (вступление в 100, сообщение в другой переписке в 200 → фильтр с 195 группу не вернёт), а `changedAfter` новые переписки в список не добавляет. Если повторный `getBatch` вернул группу в `notFoundIds` (её успели удалить), ссылка снимается, а версия попадает в курсор.

Остальные: GroupInfo по [правилам клиента](#правила-клиента-для-groupinfo).

### `groups` / `membersRemoved`

Оставшимся участникам и удалённым. Тело зависит от получателя:

| Поле `body` | Тип | Описание |
|-------------|-----|----------|
| `conversationId` | Int | Группа |
| `removedUserIds` | Int[] | Удалённые |
| `groupInfo` | GroupInfo \| null | Оставшимся — состав после изменения; удалённому — `null` |
| `removedConversation` | RemovedConversation \| null | Удалённому — метка с его новой версией; оставшимся — `null` |
| `totalUnreadCount` | Int \| null | Удалённому — общий счётчик на версии `removedConversation.changeVersion`; оставшимся — `null` |

`userIds` — `removedUserIds`.

### `groups` / `memberLeft`

Оставшимся участникам и вышедшему (во все его соединения). Тело — как у `membersRemoved`, с `leftUserId` вместо `removedUserIds`. Если вышел владелец, новый владелец виден по роли в `groupInfo`; отдельное `ownerChanged` не рассылается. `userIds` — вышедший и, если сменился, новый владелец.

### `groups` / `ownerChanged`

Всем участникам.

| Поле `body` | Тип | Описание |
|-------------|-----|----------|
| `conversationId` | Int | Группа |
| `newOwnerUserId` | Int | Новый владелец |
| `groupInfo` | GroupInfo | Состав после изменения |

`userIds` — `[newOwnerUserId]`.

### Курсор синхронизации и слияние

В таблицу [курсора синхронизации](../api/WebSocket.md#курсор-синхронизации) добавляются: `created` — `conversation.changeVersion`; `membersAdded` — `changeVersion` (у добавленного); `membersRemoved`, `memberLeft` — `removedConversation.changeVersion` (у удалённого и вышедшего). У остальных получателей версии нет, курсор не двигается. В список источников правила [слияния переписки](../api/WebSocket.md#слияние-переписки) добавляются ответ `/groups/create` и событие `created`.

Клиент, получивший метку удаления по переписке, которой нет в его загруженном списке, применяет курсор и общий счётчик — как с ReadInfo — и сохраняет [локальную метку](#объект-removedconversation): она отсечёт ответ REST, снятый до удаления.

## Алгоритмы и блокировки

Все изменения состава и владельца — в `core/Group.php` (переписка как таковая остаётся в `core/Conversation.php`), одна транзакция на метод, порядок блокировок общий ([DataModel.md](DataModel.md#транзакции-и-блокировки)):

1. `SELECT … FROM conversations WHERE id = ? FOR UPDATE` — сериализует все изменения группы: лимит 100 проверяется под блокировкой, параллельные `addMembers` его не превысят; `owner_id` и `group_info_version` читаются и меняются под ней же (проверка прав и смена владельца без гонки с `leave`).
2. Строки `conversation_members` группы (`FOR UPDATE`) — текущий состав.
3. Строки `users` по возрастанию id — **только добавленные и удалённые** (или вышедший; при создании — создатель): у `addMembers` — `SELECT id … ORDER BY id FOR UPDATE` по кандидатам (заодно проверка существования, `4001`, под блокировкой), затем `UPDATE … change_version + 1` добавленных; у удаления и выхода — `SELECT … FOR UPDATE` и multi-table `UPDATE` версии и `total_unread_count` (в нём `ORDER BY` недоступен, поэтому строки заблокированы заранее).
4. Только после этого — вставка и удаление строк `conversation_members` и `conversation_removed_members` с `change_version` из `users`.

Порядок шагов 3 и 4 обязателен: `INSERT` в `conversation_members` и `conversation_removed_members`, как и запись `conversations.owner_id` (создание группы, выход владельца), проверяет внешний ключ и ставит S-блокировку на строку `users`. Поэтому `create` поднимает версию создателя до вставки переписки, а `leave` владельца блокирует строки вышедшего и нового владельца по возрастанию id до смены `owner_id`; `changeOwner` ставит S-блокировку нового владельца под блокировкой переписки и других строк `users` не берёт — цикла нет. Если вставить строки раньше `UPDATE users`, два параллельных `addMembers` одного пользователя в разные группы (или `addMembers` и `Message::send()` с общим участником) держали бы S-блокировку и ждали X друг друга — дедлок `1213`, клиент получил бы `9001`. Когда X-блокировки `users` уже взяты по возрастанию id, проверка ключа новых ожиданий не создаёт. То же нужно в существующем `Conversation::findOrCreateSingle()` (сейчас вставка участников идёт до `bumpChangeVersion()`) — исправляется в этом же изменении.

| Операция | Что меняется |
|----------|--------------|
| `create` | `conversations` (`type = 'group'`, `name`, `description`, `avatar_file_id`, `owner_id`, `group_info_version = 1`), строка участника создателя, его `change_version` |
| `addMembers` | Новые строки участников (указатель = `last_message_id`, `unread_count = 0`), удаление их меток, `change_version` добавленных, `group_info_version + 1` |
| `removeMembers`, `leave` | Удаление строк участников, метки удаления, вычет `unread_count` из `total_unread_count` и `change_version` удалённых, при выходе владельца — `owner_id`, `group_info_version + 1` |
| `changeOwner` | `owner_id`, `group_info_version + 1` |

`updated_info_at` переписки состав не меняет. Ответ и тела событий (GroupInfo, версии, метки) собираются внутри транзакции — версии в них ровно версии этого изменения, — публикуются после коммита. Исключение — `/groups/create`: Conversation и GroupInfo новой группы читаются после коммита; это безвредно, клиент сливает их по версиям.

`/groups/getInfo` ничего не блокирует, но снимает `group_info_version` и состав в одной транзакции `REPEATABLE READ` — как `getList` снимает список и общий счётчик. Иначе между двумя запросами могло бы закоммититься изменение: состав версии N с меткой N+1 после слияния отбросил бы событие с настоящей версией N+1, и GroupInfo осталась бы устаревшей до следующего изменения.

### Проверка участия под блокировкой

Сейчас `messages/send.php`, `messages/edit.php`, `conversations/markRead.php`, `admin/sendMessage.php` и `admin/markRead.php` проверяют участие через `Conversation::isMember()` **до** транзакции. Пока участники личной переписки не менялись, это было безопасно. С удалением и выходом между проверкой и транзакцией может закоммититься удаление:

- `Conversation::markRead()` не найдёт строку участника (`$member === false`), посчитает указатель сдвинувшимся и **прибавит** `newUnread` к `total_unread_count` вместо вычитания — инвариант непрочитанных сломан, `readInfo` в ответе и событиях — `null`;
- `Message::send()` запишет сообщение уже не участника, а `readInfo` отправителя в ответе — `null` (его нет в `$readInfos`);
- `Message::edit()` изменит сообщение уже не участника и поднимет версии участников.

Поэтому `send()`, `edit()` и `markRead()` после блокировки переписки проверяют участие ещё раз — `SELECT … FROM conversation_members WHERE conversation_id = ? AND user_id = ? FOR UPDATE` (шаг 2 общего порядка) — и, если строки нет, откатывают транзакцию и сообщают вызывающему, который отвечает `5002` (`send`, `markRead`) или `6001` (`edit`). Проверка до транзакции остаётся — она отсекает чужие переписки без блокировки. Повтор `send()` с уже использованным `clientId` тоже идёт через эту проверку (она стоит до поиска по `clientId`): удалённый не получает своё старое сообщение через повтор.

## Новые коды ошибок

Невалидное название группы — существующий `1003` (`INVALID_NAME`): тот же параметр `name` с тем же лимитом 128 символов, что у пользователя; в [Errors.md](../api/Errors.md) описание кода обобщается («невалидное `name`: для пользователя — …, для группы — …») и добавляется метод. Правила допустимых символов при этом **разные**: имя пользователя в `auth/signup.php` — только буквы, цифры, `-`, `_` и пробел, а название группы — любой текст (эмодзи, пунктуация). Поэтому название и описание нормализуются так же, как текст сообщения (замена невалидного UTF-8, обрезка юникодных и невидимых пробелов по краям): код `Message::normalizeText()` переносится в `Request::normalizeText($value, $maxLength)`, а `Message::normalizeText()` вызывает его с `TEXT_MAX_LENGTH`, `Group` — с лимитами названия и описания. Лимит 128 — константа `User::NAME_MAX_LENGTH` вместо локальной `NAME_MAX_LENGTH` в `auth/signup.php`: она соответствует колонкам `users.name` и `conversations.name`, ей пользуются оба метода.

В [Errors.md](../api/Errors.md) у `5002` дополняется список методов (сейчас только `/messages/getList` и `/messages/send`, хотя код отдают и `markRead`, `getMembersReadMeta`): методы `/groups/*`, `/conversations/markRead`, `/conversations/getMembersReadMeta`; у `2003`, `1004` и `4001` — новые методы.

| Код | Константа | Описание |
|-----|-----------|----------|
| 1007 | `INVALID_DESCRIPTION` | Невалидное описание группы: длиннее 1024 символов |
| 5003 | `CONVERSATION_NOT_GROUP` | Переписка не групповая |
| 5004 | `GROUP_FORBIDDEN` | Действие доступно только владельцу группы |
| 5005 | `GROUP_MEMBERS_LIMIT` | Достигнут лимит участников группы (100) |
| 5006 | `GROUP_ALREADY_MEMBER` | Пользователь уже участник группы |
| 5007 | `GROUP_NOT_MEMBER` | Пользователь не участник группы |
| 5008 | `GROUP_OWNER_TARGET` | Действие нельзя применить к владельцу (удалить владельца, передать владение самому себе) |

## Граничные случаи

- **Добавить себя / уже добавленного** — `5006` в `notAddedUsersInfo`, не ошибка метода.
- **Добавить несуществующего** — `4001` в `notAddedUsersInfo`. Удалить несуществующего — `5007`: для удаления важно только участие.
- **Лимит при частичном заполнении**: группа на 95 участников, в запросе 10 новых — добавлены первые 5 по порядку `userIds`, остальные 5 — `5005`.
- **Удалённого добавили снова** — метка удаляется, новая строка участника с новым временем вступления и указателем = последнее сообщение; история видна целиком.
- **Выход владельца, оставшийся один участник** — он становится владельцем.
- **Выход последнего участника** — группа без участников; события получает только вышедший.
- **Параллельные `changeOwner` и `leave` владельца** — сериализуются блокировкой переписки; второй запрос видит новое состояние (`5004` или `5002`).
- **События GroupInfo в обратном порядке** — `membersAdded [5]` (версия 7) пришло после `membersRemoved [5]` (версия 8): GroupInfo версии 7 меньше локальной и отбрасывается.
- **Опоздавшие события сообщений.** `messages` / `received`, отправленное до удаления, может прийти после `membersRemoved`: клиент не знает такой переписки → `getBatch` → `notFoundIds` → событие игнорируется. Опоздавшее `membersRemoved` после повторного добавления отсекается версией (см. [RemovedConversation](#объект-removedconversation)).
- **Удаление между проверкой участия и транзакцией** `send` / `edit` / `markRead` — повторная проверка под блокировкой переписки отвечает `5002` / `6001`, счётчики и версии не меняются ([проверка участия](#проверка-участия-под-блокировкой)).
- **Ответ REST после события удаления** — `getBatch` или `getList`, снятые до удаления, отбрасываются по локальной метке `removedVersions` ([RemovedConversation](#объект-removedconversation)).
- **`getBatch` добавленного не удался** — `conversationId` остаётся в `pendingConversationIds`, запрос повторяется после переподключения; версия попадает в курсор только после ответа.
- **Параллельное добавление одного пользователя в две группы** — без дедлока: `UPDATE users` до вставки строк участников ([алгоритмы](#алгоритмы-и-блокировки)).
- **Синхронизация после оффлайна** — у удалённого метка из `removedConversations`; у добавленного, до которого не дошло событие, группа приходит по `positionUpdatedAfter` (время вступления позже всего, что клиент видел до разрыва), а если событие дошло, но не дошёл `getBatch`, — повтором из `pendingConversationIds`; у остальных GroupInfo открытой группы перезапрашивается после переподключения, закрытых — при открытии.
- **Нагрузка.** Сообщение в группе на 100 участников — 100 строк `conversation_members` и 100 строк `users` в транзакции отправки и 100 доставок WS; `markRead` рассылает `memberRead` 99 участникам. Для лимита 100 приемлемо (см. [UnreadMessages.md](UnreadMessages.md#граничные-случаи-и-риски), [ReadReceipts.md](ReadReceipts.md#на-будущее)); изменение состава при этом пишет только строки затронутых пользователей. Увеличение лимита потребует пересмотра.
- **Спам-приглашения.** Добавить можно любого пользователя без его согласия; ограничение — в будущих настройках приватности.
- **Админ-панель** использует `memberIds` — для групп он `null`, состав групп в админке не показывается.

## Принятые решения

| Вопрос | Решение |
|--------|---------|
| Где хранить владельца | Колонка `conversations.owner_id`: ровно один владелец гарантирован схемой. В API — роль в GroupInfo |
| Состав и роли | Отдельная сущность GroupInfo со своей версией группы; запрос при открытии группы + события, как мета прочтения |
| `memberIds` в Conversation | Для `group` — `null` (тип Int[] \| null); для `single` — как сейчас |
| Изменение состава для остальных участников | Не меняет Conversation, `updatedInfoAt` и версию пользователя; событие с GroupInfo вне курсора |
| Добавленный | Событие с `conversationId` и его версией, Conversation — через `getBatch` |
| Удаление и выход | Строка участника удаляется + метка в `conversation_removed_members`; существующие проверки участия остаются, изменяющие методы дополнительно проверяют участие под блокировкой |
| Синхронизация удаления | `removedConversations` в `getList` с `changedAfter`, общий курсор версий |
| Позиция добавленного | `positionUpdatedAt` зависит от смотрящего: максимум времени последнего сообщения и вступления |
| Прочтение нового участника | Указатель = последнее сообщение, `unreadCount = 0` |
| Правило протокола | «Версия + идемпотентное применение» (полный объект или ссылка с версией) + обязательный путь восстановления после потерянного события вместо «полный объект» |
| Курсор при ссылке | Версия события-ссылки попадает в курсор только после успешного REST; неудачные — в `pendingConversationIds` с повтором после переподключения |
| Удаление на клиенте | Локальная метка `removedVersions` и для незагруженных переписок: отсекает ответы REST, снятые до удаления |
| Проверка участия | Повторно под блокировкой переписки в `send()`, `edit()`, `markRead()` |
| Статус «прочитано» в группе | Только по участникам из GroupInfo и сообщениям после их `joinedAfterMessageId` |
| Превью в списке групп | `senderId` в LastMessage |
| Пользователи в мете прочтения | action `users` в `getMembersReadMeta`, `userIds` в `memberRead` |
| `getMembersInfo` | Заменён на `getInfo` с GroupInfo |
| Ответы изменяющих методов | Возвращают `groupInfo` после изменения; `leave` — метку и общий счётчик |
| Частичное добавление | Успех с `addedUserIds` и `notAddedUsersInfo`; события только если кто-то добавлен |
| Лимит | 100 участников включая владельца, константа `Group::MAX_MEMBERS`; проверка под блокировкой переписки |
| Владелец удаляет себя | Нельзя (`5008`), выход — `/groups/leave` |
| Смена владельца при выходе | Видна по роли в `groupInfo` события `memberLeft`, отдельного `ownerChanged` нет |
| Новый владелец при выходе | Самый давний участник (раньше вступил, затем меньший `userId`) |
| Название | Поле и колонка `name`, ошибка — существующий `1003` |
| Параметр аватара | `avatarFileId` |
| Идемпотентность `create` | Не делается |
| Группа без участников | Не удаляется |
| Начальные участники в `create` | Не делаются: создание, затем `addMembers` |
| Что видит удалённый | Переписка удаляется из списка и кэша целиком; «только чтение» — на будущее |

## Отличия от исходной постановки

| В постановке | В документе | Почему |
|--------------|-------------|--------|
| `title` | `name` | Поле `name` у Conversation уже есть, как и у `User` |
| `avatarId` | `avatarFileId` | Передаётся id файла — как `fileId` в `/profile/setAvatar` |
| `group/changeOwner` без `conversationId` | `groups/changeOwner` с `conversationId` | Префикс как у остальных методов; без id не определить группу |
| `getMembersInfo`: `ownerId` и `memberIds` без владельца | `getInfo`: GroupInfo с ролями | Формат переживёт появление модераторов |
| События `addedMembers`, `kickedMembers`, `leavedMember`, `ownerChanger` | `membersAdded`, `membersRemoved`, `memberLeft`, `ownerChanged` | По образцу `singleCreated`, `memberRead`; `membersRemoved` — пара к `removeMembers` |
| События несут только id | Добавленному — id и версия, удалённому — метка и счётчик, остальным — GroupInfo | [Правило протокола](#правило-протокола-для-событий): версия и идемпотентность |
| Новый владелец при выходе — случайный | Самый давний участник | Предсказуемо и тестируемо |
| — | Ответы изменяющих методов несут `groupInfo` | Клиенту владельца не нужно ждать события |

## На будущее

- Изменение названия, описания и аватара — методы владельца, изменение информации Conversation (`updatedInfoAt` + версия всех участников + событие).
- Системные сообщения о добавлении, удалении, выходе и смене владельца — поднимут позицию естественным путём.
- Роли (модераторы): колонка роли в `conversation_members`, новые значения `GroupMember.role`, проверка прав по роли вместо `owner_id`.
- Настройки приватности: запрет приглашения — новый код в `notAddedUsersInfo`.
- Чистка старых меток удаления.
- Переписка «только для чтения» для удалённого: история до момента удаления остаётся у него в списке.
