# Непрочитанные сообщения: счётчики и прочтение

[← Обзор архитектуры](Overview.md)

Описывает, как сервер считает непрочитанные сообщения по каждой переписке и в сумме, как пользователь отмечает переписку прочитанной и как клиент синхронизирует прочтение между устройствами. Реализовано; клиентский контракт — в `docs/api/` ([ReadInfo и версия пользователя](../api/Objects.md#объект-readinfo), [методы переписок](../api/methods/Conversations.md), [слияние переписки](../api/WebSocket.md#слияние-переписки) и [курсор синхронизации](../api/WebSocket.md#курсор-синхронизации), [события `conversations`](../api/websocket/Conversations.md) и [`messages`](../api/websocket/Messages.md)), здесь — серверная сторона и обоснования. При расхождении верен `docs/api/`.

## Коротко

- Прочтение — это указатель `lastReadMessageId` на пару (переписка, пользователь). Всё, что не новее указателя, прочитано. Своё сообщение сдвигает указатель на себя.
- В **Conversation** добавляются `unreadCount`, `lastReadMessageId` и `changeVersion`. Новый объект **ReadInfo** объединяет их с общим счётчиком `totalUnreadCount`.
- У пользователя одна монотонная версия `changeVersion`. Она растёт при любом изменении его переписок, кроме позиции в списке: при прочтении, новом сообщении и изменении информации переписки.
- `/conversations/getList`: фильтр **`changedAfter`** по этой версии заменяет `updatedInfoAfter` / `updatedInfoAfterId` (ломающее изменение). В каждом ответе появляются `totalUnreadCount` и `changeVersion`.
- Новые методы: **`/conversations/markRead`** и **`/global/getTotalUnreadCount`**. Ответ `/messages/send` получает `readInfo` отправителя.
- Новое WS-событие **`conversations` / `read`**. `messages` / `received` получает `readInfo`, своё для каждого получателя; `messages` / `edited` при правке последнего сообщения — `changeVersion` получателя.
- Каждое изменение, поднимающее версию, приходит событием с этой версией. Курсор синхронизации события двигают только по **правилу непрерывности**: без пропусков версий.

## Правила прочтения

- Сообщение от другого участника не прочитано пользователем, пока тот его не прочтёт.
- Своё сообщение всегда прочитано. Отправка сообщения также отмечает прочитанной всю переписку до него.
- Отдельного статуса у каждого сообщения нет: всё, что с id не больше `lastReadMessageId`, прочитано.
- Указатель только растёт: прочтение более старого сообщения ничего не меняет.

## Модель данных

Мета прочтения хранится в существующей таблице `conversation_members` (строка = пара conversationId / userId), общий счётчик — в `users`. Отдельная таблица не нужна: пара уже есть и уже джойнится во всех выборках переписок пользователя.

| Таблица | Колонка | Тип | Поле API | Смысл |
| --- | --- | --- | --- | --- |
| `conversation_members` | `last_read_message_id` | INT UNSIGNED NOT NULL DEFAULT 0 | `lastReadMessageId` | Указатель прочтения; 0 — ничего не прочитано |
| `conversation_members` | `unread_count` | INT UNSIGNED NOT NULL DEFAULT 0 | `unreadCount` | Непрочитанные в переписке |
| `conversation_members` | `change_version` | INT UNSIGNED NOT NULL DEFAULT 0 | `changeVersion` | Версия пользователя на момент последнего изменения переписки для него |
| `users` | `total_unread_count` | INT UNSIGNED NOT NULL DEFAULT 0 | `totalUnreadCount` | Сумма `unread_count` по всем перепискам |
| `users` | `change_version` | INT UNSIGNED NOT NULL DEFAULT 0 | `changeVersion` | Версия пользователя: +1 на любое изменение его переписок, кроме позиции |

`lastMessageId` в строке участника не хранится: он уже есть в `conversations.last_message_id` и одинаков для всех участников. Копия была бы лишним источником рассинхрона и лишней записью на каждое сообщение.

### Единая версия

У пользователя одна шкала — `users.change_version`. Она растёт на 1 с каждым изменением, которое пользователь видит в Conversation и которое не двигает переписку в списке:

- прочтение (`markRead`) и новое сообщение — меняются поля прочтения;
- информация переписки — всё, что двигает `updated_info_at`: название, аватар, участники, правка последнего сообщения;
- создание переписки — строки участников сразу получают новую версию.

Изменённая строка `conversation_members` получает новое значение `users.change_version`. Изменение, которое затрагивает всех участников, увеличивает версию у каждого. Одна и та же версия служит курсором фильтра `changedAfter` и версией слияния полей прочтения и общего счётчика. Информация переписки по-прежнему сливается по `updatedInfoAt` (см. [Изменения в Conversation](#изменения-в-conversation)).

За одно увеличение версии меняется не больше одной строки пользователя, поэтому ненулевые `change_version` одного пользователя не повторяются. Ключ `KEY user_change_version (user_id, change_version)` на `conversation_members` обслуживает фильтр `changedAfter`.

### Миграция

`db/013_unread.sql`. Всё существующее считается прочитанным: `last_read_message_id = COALESCE(conversations.last_message_id, 0)`, `unread_count = 0`, `total_unread_count = 0`, все `change_version = 0`. Клиенты после обновления всё равно загружают список заново.

## Алгоритмы обновления

Все сценарии идут в одной транзакции с блокировкой строки переписки (`SELECT … FOR UPDATE`), как уже делает `Message::send`. Порядок блокировок везде один: `conversations` → строка `conversation_members` инициатора → `users`. Каждое изменение для пользователя — это `users.change_version + 1`, и его строка `conversation_members` получает это новое значение.

readInfo для ответа и событий собирается внутри транзакции перед коммитом, одним запросом `conversation_members m JOIN users u`: строки уже заблокированы, поэтому `changeVersion` — ровно версия этого изменения, а `totalUnreadCount` снят на ней же. После коммита строку `users` могло уже изменить другое изменение. Счётчик, перечитанный тогда, оказался бы помечен чужой версией. Этого требует и [правило непрерывности](#get-conversationsgetlist--фильтр-changedafter).

Вычитания из `total_unread_count` идут через `GREATEST(CAST(total_unread_count AS SIGNED) - …, 0)`. Колонка UNSIGNED, и в strict mode уход ниже нуля — ошибка 1690. Сломанный счётчик иначе блокировал бы отправку сообщений и `markRead`. Расхождение ловят проверка инварианта и хелпер пересчёта (см. [Граничные случаи](#граничные-случаи-и-риски)).

### Новое сообщение

Логика кладётся в `Message::send`, чтобы её получили и `/messages/send`, и `admin/sendMessage.php`. При повторе с тем же `clientId` ничего не меняется.

1. Прочитать `unread_count` отправителя (`SELECT … FOR UPDATE`) — это `delta`.
2. Один UPDATE `users` по всем участникам (`WHERE id IN (…) ORDER BY id`): `change_version + 1`; `total_unread_count = GREATEST(CAST(total_unread_count AS SIGNED) + IF(id = :senderId, -:delta, 1), 0)` — минус `delta` у отправителя, плюс 1 у остальных.
3. Один `UPDATE conversation_members m JOIN users u ON u.id = m.user_id` по строкам переписки: `m.change_version = u.change_version`; у отправителя `last_read_message_id = id`, `unread_count = 0`; у остальных `unread_count + 1`.
4. До коммита — прочитать readInfo всех участников одним запросом. После коммита — разослать `messages` / `received` через `WebSocket::publishEach`, у каждого получателя свой readInfo. readInfo отправителя также уходит в ответ `/messages/send`.

Версия отправителя растёт всегда, даже при `delta = 0`: у него сдвигается указатель. В шаге 3 чтение `u.change_version` безопасно: этот UPDATE `users` не меняет. `delta` читается отдельно, потому что в multi-table UPDATE MySQL не гарантирует порядок присваиваний. Все строки `users` обновляются одним запросом с явным `ORDER BY id`, поэтому параллельные отправки в разные переписки не сцепляются в дедлок. Без `ORDER BY` порядок блокировок зависел бы от плана запроса.

### Прочтение (`/conversations/markRead`)

1. Проверить участие в переписке и что `messageId` принадлежит этой переписке.
2. В транзакции заблокировать переписку и строку участника.
3. `messageId <= last_read_message_id` → ничего не менять, версию не увеличивать, вернуть текущий readInfo без WS-события.
4. `messageId = conversations.last_message_id` → `newUnread = 0`; иначе `newUnread = COUNT(*) FROM messages WHERE conversation_id = ? AND id > messageId` (индекс `conversation_id (conversation_id, id)` уже есть).
5. `delta = unread_count - newUnread`; `users`: `change_version + 1`, `total_unread_count = GREATEST(CAST(total_unread_count AS SIGNED) - delta, 0)`.
6. Строка участника: `last_read_message_id = messageId`, `unread_count = newUnread`, `change_version` = новая `users.change_version`.
7. До коммита — прочитать readInfo. После коммита — `conversations` / `read` во все соединения пользователя и readInfo в ответе.

В шаге 4 фильтр `sender_id <> userId` не нужен: своё сообщение всегда сдвигает указатель, поэтому после него стоят только чужие сообщения. Ветка «прочитано последнее» — лишь оптимизация общего случая.

### Изменение информации переписки

Любой код, который меняет `conversations.updated_info_at`, в той же транзакции увеличивает версию всех участников. Это выносится в общий хелпер, например `Conversation::bumpChangeVersion($conversationId)`:

1. Один UPDATE `users` по участникам (`ORDER BY id`): `change_version + 1`.
2. Один `UPDATE conversation_members m JOIN users u` по строкам переписки: `m.change_version = u.change_version`.
3. До коммита — прочитать новые версии участников (`user_id → change_version`) и вернуть их. Их несёт событие изменения: `changeVersion` в `messages` / `edited`, `conversation.changeVersion` в `singleCreated`.

Сейчас таких мест два: правка последнего сообщения (`Message::edit`, если `isLast`) и создание личной переписки (`Conversation::findOrCreateSingle`). Позже добавятся название, аватар и участники групп. В личных чатах это 2 + 2 строки.

## API

### Объект ReadInfo

Состояние прочтения одной переписки для текущего пользователя плюс его общий счётчик — снимок на одной версии. Новый раздел в `docs/api/Objects.md`.

| Поле | Тип | Описание |
| --- | --- | --- |
| `conversationId` | Int | Переписка |
| `lastReadMessageId` | Int | Последнее прочитанное сообщение; `0` — ничего не прочитано (id сообщений начинаются с 1, поэтому сравнения не требуют особого случая) |
| `unreadCount` | Int | Непрочитанные в переписке |
| `totalUnreadCount` | Int | Непрочитанные по всем перепискам |
| `changeVersion` | Int | Версия пользователя (`users.change_version`), на которой сняты все поля выше; в событии — версия именно этого изменения |

```json
{
  "conversationId": 1,
  "lastReadMessageId": 15,
  "unreadCount": 0,
  "totalUnreadCount": 3,
  "changeVersion": 118
}
```

Все поля читаются одним запросом вместе с `users.change_version`. Поля переписки на этой версии тоже верны: её строку с версии `m.change_version` никто не менял. В событиях readInfo собирается в транзакции изменения (см. [Алгоритмы обновления](#алгоритмы-обновления)).

Клиент хранит `changeVersion` у каждой переписки и отдельно у общего счётчика. Поля прочтения переписки он берёт, если пришедший `changeVersion` больше её локального; `totalUnreadCount` — если больше локальной версии счётчика. Шкала одна, поэтому счётчик из события по любой переписке корректно сравнивается со счётчиком из `getTotalUnreadCount`. Версия переписки растёт и при изменении информации — тогда поля прочтения приходят те же, и их повторное применение безвредно.

### Изменения в Conversation

Добавляются `unreadCount`, `lastReadMessageId`, `changeVersion`; `totalUnreadCount` в Conversation не входит. Значения зависят от смотрящего, как и `opponentUserId`: `Conversation::select()` джойнит `conversation_members` по `viewerId`. Этот JOIN заменяет собственные `JOIN conversation_members m` в `findByIds` и `findListByMember`, а `findById`, где его сейчас нет, получает его вместе с `select()`.

В [правила слияния](../api/WebSocket.md#слияние-переписки) добавляется четвёртое: если пришедший `changeVersion` больше локального, взять `unreadCount`, `lastReadMessageId`, `changeVersion`. Информация по-прежнему сливается по `updatedInfoAt` (правило 3). Перевести её на `changeVersion` нельзя: события `messages` несут версию, но не информацию, и применённая из события версия отбросила бы ещё не пришедшие изменения информации.

### `GET /conversations/getList` — фильтр `changedAfter`

`changedAfter` заменяет `updatedInfoAfter` и `updatedInfoAfterId`: одним запросом отдаёт переписки, у которых изменилась информация или прочтение, в том числе на другом устройстве. Фильтров синхронизации остаётся два: `positionUpdatedAfter` и `changedAfter`. Изменение ломающее: проект не в проде, клиент обновляется вместе с сервером.

| Параметр | Тип | Описание |
| --- | --- | --- |
| `changedAfter` | Int | Только переписки с `changeVersion` строго больше значения. Сортировка — по возрастанию `changeVersion`; следующая страница — `changedAfter` = `changeVersion` последней полученной переписки. Не сочетается с `offset` и `positionUpdatedAfter` (ошибка `1004`) |

В любом ответе `getList` появляются поля верхнего уровня `totalUnreadCount` и `changeVersion` — текущие у пользователя. Сервер читает их в той же транзакции, что и список.

Выборка `changedAfter` идёт от `conversation_members` по ключу `(user_id, change_version)` с `ORDER BY m.change_version LIMIT` (`STRAIGHT_JOIN`, как в `Message::findBlocksByIds`). Иначе оптимизатор может начать с `conversations` и сортировать все переписки пользователя.

Запас «минус несколько секунд», который был у `updatedInfoAfter`, больше не нужен. Версия — счётчик под блокировкой строки `users`, и версия N+1 не появится раньше коммита версии N. У `positionUpdatedAfter` запас остаётся.

**Синхронизация.** После каждого (пере)подключения WebSocket выполняются два независимых запроса: `positionUpdatedAfter`, как сейчас, и `changedAfter` вместо `updatedInfoAfter`. Клиент хранит `syncedChangeVersion` — версию, до которой он видел все изменения, — и множество `seenVersions`: версии выше курсора, пришедшие в событиях. `maxUpdatedInfoAt` больше не нужен.

При первой загрузке списка (по `offset`) `syncedChangeVersion` = `changeVersion` верхнего уровня **первой** страницы. Изменения во время листания получают версию больше, и их догонит следующая синхронизация. Курсор с последней страницы перескочил бы изменения переписок, загруженных на предыдущих страницах.

1. Запрос с `changedAfter = syncedChangeVersion`.
2. Пока `hasNext: true` — следующая страница курсором. Переписка, изменившаяся во время листания, уходит в конец выдачи и не теряется.
3. Полученные переписки сливаются только с уже загруженными — по всем правилам слияния, как сейчас у `updatedInfoAfter`; новые в список не добавляются. Изменения прочтения в незагруженных переписках учтены в `totalUnreadCount` ответа.
4. После последней страницы `syncedChangeVersion` = максимум из `changeVersion` ответа и полученных переписок. Версии не выше курсора убираются из `seenVersions`, затем курсор продвигается по правилу непрерывности.
5. Дальше курсор двигают события по правилу непрерывности. События, пришедшие во время синхронизации, применяются и попадают в `seenVersions` как обычно.

**Правило непрерывности.** Каждое изменение увеличивает версию пользователя ровно на 1 и доставляется во все его соединения событием с версией этого изменения:

| Изменение | Событие | Версия |
| --- | --- | --- |
| Прочтение (`markRead`) | `conversations` / `read` | `readInfo.changeVersion` |
| Новое сообщение | `messages` / `received` | `readInfo.changeVersion` |
| Правка последнего сообщения | `messages` / `edited` | `changeVersion` |
| Создание личной переписки | `conversations` / `singleCreated` | `conversation.changeVersion` |

Событие с версией `v` всегда применяется по правилам слияния. Если `v > syncedChangeVersion`, `v` добавляется в `seenVersions`. Затем, пока `syncedChangeVersion + 1` есть в `seenVersions`, курсор растёт на 1, а версия убирается из множества.

Курсор не перескакивает версию, событие которой не дошло. Доставка по WS идёт без повторов ([WebSocket.md](WebSocket.md)), а события параллельных запросов публикуются после коммита и могут прийти не в порядке версий. Пропуск остаётся до следующей синхронизации: `changedAfter` с курсора вернёт пропущенное изменение, а заодно и уже полученные выше него (повторное слияние безвредно). Если разрыв держится дольше нескольких секунд, клиент может запустить синхронизацию `changedAfter`, не дожидаясь переподключения.

Ответы методов (`markRead`, `/messages/send`) применяются слиянием, но курсор не двигают: то же изменение приходит событием во все соединения пользователя, включая вызвавшее.

### `POST /conversations/markRead`

Отмечает прочитанными сообщения переписки до `messageId` включительно. Идемпотентен: повтор или более старый `messageId` возвращает текущий readInfo без изменений.

| Параметр | Тип | Описание |
| --- | --- | --- |
| `conversationId` | Int | Переписка |
| `messageId` | Int | Последнее прочитанное сообщение |

Ответ: `readInfo` (ReadInfo).

Ошибки: `5002 CONVERSATION_NOT_FOUND` — нет переписки или пользователь не участник; `6001 MESSAGE_NOT_FOUND` — сообщения нет или оно из другой переписки. Новые коды не нужны.

### `GET /global/getTotalUnreadCount`

Без параметров. Ответ: `totalUnreadCount`, `changeVersion`. Требует авторизации.

### `POST /messages/send` — новое поле `readInfo`

В ответ рядом с `message` добавляется `readInfo` отправителя. Отправитель обновляет счётчики, не дожидаясь события, — так же, как после `markRead`. Для новой отправки `unreadCount = 0`, `lastReadMessageId = message.messageId`. При повторе с тем же `clientId` отдаётся текущий readInfo переписки: версия не растёт, `lastReadMessageId` может быть больше `message.messageId`, а более поздние чужие сообщения уже учтены в счётчиках.

## WebSocket

### `conversations` / `read` — переписка прочитана

Событие группы `conversations`: меняется состояние переписки, а не сообщения, и метод — `/conversations/markRead`. Описание — в `docs/api/websocket/Conversations.md`, рядом с `singleCreated`.

Приходит во все соединения пользователя, вызвавшего `/conversations/markRead`, — в том числе в соединение устройства, с которого прочитали (повторное применение отсекается версиями). Другим участникам не рассылается. Если markRead ничего не изменил, события нет.

| Поле `body` | Тип | Описание |
| --- | --- | --- |
| `readInfo` | ReadInfo | Новое состояние прочтения переписки и общий счётчик |

Клиент применяет поля переписки и общий счётчик независимо, каждый по своей локальной версии, сравнивая их с одним `changeVersion` события. Переписку, которой нет в загруженном списке, по этому событию не загружают, но общий счётчик применяют. Курсор синхронизации событие двигает по [правилу непрерывности](#get-conversationsgetlist--фильтр-changedafter).

### `messages` / `received` — новое поле `readInfo`

В `body` добавляется `readInfo` — состояние для получателя события. У отправителя `unreadCount = 0` и `lastReadMessageId = message.messageId`, у остальных — увеличенный счётчик. Тело события теперь разное для каждого получателя, поэтому `WebSocket::publish` в `messages/send.php` заменяется на `publishEach` с одной доставкой на участника (как сейчас, один HTTP-запрос к WS-серверу).

### `messages` / `edited` — новое поле `changeVersion`

Прочтение правка не меняет, readInfo событие не получает. Правка последнего сообщения (в `body` есть `lastMessage`) увеличивает `changeVersion` участников, и событие получает поле `changeVersion` — новую версию получателя. Без него курсор синхронизации остановился бы на этой версии до переподключения. Тело тогда своё у каждого получателя, поэтому `WebSocket::publish` в `messages/edit.php` заменяется на `publishEach`. Правка не последнего сообщения версию не меняет и поля не несёт.

`conversations` / `singleCreated` уже отдаёт каждому участнику свою Conversation; её `changeVersion` и есть версия события.

## Принятые решения

| Вопрос | Решение |
| --- | --- |
| Синхронизация после оффлайна | Единая версия пользователя `change_version` и фильтр `changedAfter` вместо `updatedInfoAfter`. Без неё клиент не узнал бы о прочтении на другом устройстве: прочтение не меняет ни `positionUpdatedAt`, ни `updatedInfoAt` |
| Общая шкала для информации и прочтения | Счётчик, а не время: нет запаса и дублей при синхронизации, работает индекс, курсор — одно число. Цена — изменение информации пишет 2N строк |
| `lastMessageId` в строке участника | Не хранить: он уже есть в `conversations.last_message_id` |
| Порядок блокировок `users` | Все строки `users` — одним UPDATE с явным `ORDER BY id`, отправитель включён |
| Курсор синхронизации и события | Правило непрерывности: событие двигает курсор, только закрывая версию `syncedChangeVersion + 1`; версию несут все события, которые её поднимают. Доставка по WS не гарантирована и не упорядочена, поэтому перескок через версию терял бы изменение |
| Версия readInfo в событии | Версия самого изменения: readInfo собирается в транзакции до коммита |
| Уход счётчиков ниже нуля | Вычитание через `GREATEST(… , 0)`: ошибка счётчика не блокирует отправку |
| Имя WS-события | `conversations` / `read` |
| Общий счётчик в Conversation | Не включать: он повторился бы в каждой переписке списка. Отдаётся полями верхнего уровня `getList` |
| Заполнение существующих данных | Всё старое прочитано: указатель = последнее сообщение переписки, счётчики = 0 |
| `lastReadMessageId`, когда ничего не прочитано | `0`; колонка NOT NULL DEFAULT 0, тип в API — Int |
| readInfo в ответе `/messages/send` | Да, readInfo отправителя |
| `totalUnreadCount` и `changeVersion` в `getList` | В каждом ответе, полями верхнего уровня |

**Правило для документации** (рядом с правилом про полный объект в [синхронизации](../api/WebSocket.md#синхронизация)): любое новое изменяемое поле переписки, кроме позиции, обязано увеличивать `change_version` участников, иначе синхронизация его потеряет. Событие этого изменения обязано нести новую версию получателя, иначе курсор остановится на ней до переподключения.

## Граничные случаи и риски

- **Инвариант в тестах.** `total_unread_count = SUM(unread_count)` — денормализация, которая расходится при любой ошибке. Нужен хелпер пересчёта (для тестов и ручного исправления) и проверка инварианта после каждого API-теста прочтения. `GREATEST(…, 0)` в вычитаниях не даёт расхождению сломать отправку, но и скрывает его — поэтому проверка инварианта обязательна.
- **Удаление данных ломает счётчики.** Удаление пользователя каскадом удаляет его сообщения, а `unread_count` у других остаётся. Когда появятся удаление сообщений и выход из группы, им понадобятся пересчёт затронутых строк и readInfo в событии. Выход из группы к тому же не попадёт в `changedAfter` для вышедшего, потому что его строки участника больше нет: понадобится метка удаления (tombstone) или отдельный механизм.
- **Большие группы.** Каждое сообщение и каждое изменение информации пишут N строк `conversation_members` и N строк `users`. Для личных чатов это 2 + 2, для групп на тысячи участников — уже дорого. Тогда `unreadCount` стоит считать лениво (COUNT от указателя с потолком, скажем, 999).
- **Правила для клиента в документации.** markRead вызывается с id последнего видимого сообщения и с debounce при прокрутке; не отправляется, если id не больше локального `lastReadMessageId`. Локальное смещение указателя — оптимистичное, ответ или событие подтверждают его по версии.

## На будущее

- **Счётчик в `/global/start`.** Клиент всё равно вызывает его при запуске. Если отдавать там `totalUnreadCount` и `changeVersion` (или `null` для анонима), на старте будет одним запросом меньше. `getTotalUnreadCount` остаётся для фонового обновления бейджа.
- **«Прочитано собеседником» (две галочки).** Реализовано по [ReadReceipts.md](ReadReceipts.md): отдельный метод `/conversations/getMembersReadMeta` и событие `conversations` / `memberRead` без версий вместо поля `opponentLastReadMessageId` в Conversation.
- **«Отметить непрочитанным» и «прочитать всё».** Первое ломает монотонность указателя — если понадобится, то отдельным флагом, а не откатом `lastReadMessageId`. Второе — отдельный метод с одним событием на все переписки.
