# Файлы: загрузка и хранение

[← Обзор архитектуры](Overview.md)

Сейчас загружаются только изображения (`/files/uploadImage`) — они используются как аватары. Клиентский контракт — [methods/Files.md](../api/methods/Files.md), [объект File](../api/Objects.md#объект-file), [methods/Profile.md](../api/methods/Profile.md); здесь — серверная сторона.

Код: `files/uploadImage.php` (проверки запроса), `core/File.php` (сохранение, уменьшенная копия, сущность), `profile/setAvatar.php`, `profile/removeAvatar.php`. Настройки — `config/files.php`.

## Хранение

- **Диск.** Файлы лежат в `static/uploads/ГГГГ/ММ/` (`UPLOAD_DIR` + месяц загрузки), каталоги создаются по мере надобности. Имя — 32 случайных hex-символа (`random_bytes(16)`), уменьшенная копия — тот же базовый путь с суффиксом `_small`:

  ```
  static/uploads/2026/10/3f9c…e1.jpg
  static/uploads/2026/10/3f9c…e1_small.jpg
  ```

  Имя не зависит от имени, присланного клиентом, поэтому его нельзя угадать или использовать для обхода пути.
- **Отдача** — nginx как статика (`location /static/`, `X-Content-Type-Options: nosniff`, PHP в этом каталоге не исполняется). Через PHP файлы не проходят и доступ к ним не проверяется: кто знает URL, тот может скачать файл.
- **БД** — запись в `files` ([DataModel.md](DataModel.md#files--загруженные-файлы)): путь относительно корня проекта, размер, имя для показа, расширение, `data` с `small_path`.
- **URL** строится при каждой выдаче: `BASE_URL` + путь. Хост берётся из конфига, а не из заголовка `Host` запроса, — так его нельзя подменить, а смена домена не требует миграции данных.

## Загрузка изображения

`files/uploadImage.php` проверяет сам запрос:

1. авторизация (`2003`);
2. файл передан в поле `file` (`3001`);
3. размер: превышение `upload_max_filesize` / `MAX_FILE_SIZE` формы или `UPLOAD_MAX_SIZE` (10 МБ) → `3002`; прочие ошибки загрузки PHP → `3005`;
4. имя для показа — параметр `filename` или исходное имя файла (`basename`), невалидный UTF-8 заменяется (`mb_scrub`), обрезка до 255 символов.

Дальше `File::storeImage()`:

1. **Тип — по содержимому, а не по имени.** MIME определяет `finfo`; допустимы `image/jpeg`, `image/png`, `image/webp` (`File::IMAGE_MIMES`), расширение на диске берётся из MIME. Затем `getimagesize()` должен прочитать размеры. Иначе — `3003`. GIF изображением не считается: для анимаций предполагается отдельный тип.
2. **Лимит пикселей до декодирования.** Ширина × высота из заголовка не больше `IMAGE_MAX_PIXELS` (25 Мп), иначе `3002`. GD держит картинку в памяти несжатой (4 байта на пиксель, при повороте — две копии), и маленький файл может распаковаться в гигабайты.
3. **Перенос** во `static/uploads/ГГГГ/ММ/` (`move_uploaded_file`); ошибка — `3005`.
4. **Уменьшенная копия** — меньшая сторона не больше `IMAGE_SMALL_SIDE` (200 px):
   - если исходник уже меньше — просто копия файла;
   - иначе на время обработки поднимается `memory_limit` до `IMAGE_MEMORY_LIMIT` (256M), изображение декодируется и масштабируется `imagecopyresampled`;
   - у JPEG ориентация из EXIF (`Orientation` 2–8) применяется к пикселям — `imagejpeg` EXIF не сохраняет, и без этого миниатюра с телефона легла бы на бок. Без расширения `exif` шаг пропускается;
   - у PNG и WebP сохраняется прозрачность;
   - качество: JPEG и WebP — 85, PNG — сжатие 6;
   - исходный файл не перекодируется и хранится как прислали (вместе с EXIF).
5. **Запись в `files`** и возврат сущности.

Если на шагах 4–5 что-то сломалось (битые данные изображения, ошибка БД), оба файла удаляются с диска: на диске не остаётся файлов без записи в БД. Обратное не гарантируется — см. ниже.

## Аватар

- `/profile/setAvatar` ставит `users.avatar_file_id`. Файл должен принадлежать текущему пользователю (`files.user_id`), иначе `3004` — чужой файл неотличим от несуществующего; не изображение — `3003`.
- `/profile/removeAvatar` обнуляет `avatar_file_id`. Запись в `files` и файлы на диске остаются.
- Аватар отдаётся в объекте User целиком как File — `User::fromRow()` собирает его из того же запроса (`LEFT JOIN files`, колонки с префиксом `f_`).
- Колонка `conversations.avatar_file_id` предназначена для аватаров групповых переписок; групповые пока не создаются.

## Чего нет

- **Удаления файлов.** Ни метода удаления, ни очистки неиспользуемых файлов нет: замена и удаление аватара оставляют старый файл. При удалении пользователя записи `files` удаляются каскадом, а файлы на диске — нет. Если это станет проблемой, нужна фоновая очистка файлов без записи / записей без ссылок.
- **Проверки доступа.** `/files/get` отдаёт информацию о любом файле по `fileId` без авторизации, сами файлы доступны по URL. Для приватных вложений в сообщениях понадобится отдача через PHP или подписанные ссылки.
- **Типа `other`.** Он есть в схеме и в `File::fromRow()` (`data` — пустой объект), но загрузки произвольных файлов нет.
