# Архитектура: общий обзор

[← README](../../README.md)

ServerAi — бэкенд мессенджера на чистом PHP без фреймворка и зависимостей: REST API + отдельный WebSocket-сервер, одна БД MySQL. Документ описывает, как устроен код в целом; отдельные механизмы — в соседних документах раздела (см. [Документы раздела](#документы-раздела)). Клиентский контракт — [docs/api/](../api/README.md).

## Компоненты

```
клиент ──HTTP──▶ index.php (роутер) ──▶ обработчик метода (auth/, messages/, …) ──▶ core/ ──▶ MySQL
   │                                                   │ publish / closeSession
   │                                                   ▼ (HTTP на 127.0.0.1)
   └────WS────▶ websocket/server.php (WsServer) ─────────────────────────────────▶ MySQL (только токены)
```

| Компонент | Где | Что делает |
|-----------|-----|------------|
| REST API | `index.php` + каталоги методов | Один запрос — один короткоживущий PHP-процесс (PHP-FPM или `php -S`). Всё состояние — в MySQL и файлах сессий |
| WebSocket-сервер | `websocket/` | Долгоживущий CLI-процесс: держит соединения клиентов и рассылает им события, которые присылает API. Подробно — [WebSocket.md](WebSocket.md) |
| Админ-панель | `admin/` | HTML-страница `/admin` и JSON-методы для действий от имени пользователя. Контракт — [docs/api/Admin.md](../api/Admin.md) |
| Хранилище | MySQL, `static/uploads/`, `storage/sessions/` | Данные — [DataModel.md](DataModel.md), файлы — [Files.md](Files.md), сессии — [Sessions.md](Sessions.md) |

## Структура репозитория

```
index.php               роутер REST API: карта «путь → файл обработчика»
global/ auth/ profile/  обработчики методов — по одному файлу на метод,
files/ users/           каталог = префикс URL (/messages/send → messages/send.php)
conversations/ messages/
admin/                  админ-панель: index.php (страница) и её методы
core/                   общий код: инфраструктура и сущности
websocket/              WebSocket-сервер (server.php — точка входа)
config/                 настройки; db.php и app.php — локальные, не в git
db/                     миграции схемы БД, NNN_описание.sql
static/uploads/         загруженные пользователями файлы (не в git)
static/docs/            статичные документы (лицензия, политика конфиденциальности)
storage/sessions/       файлы PHP-сессий (создаётся сам, не в git)
tests/                  раннер, библиотека тестов, юнит- и API-тесты
docs/                   документация
```

## Жизненный цикл запроса

1. **Вход.** nginx передаёт в `index.php` всё, кроме `/static/` и `/ws` (см. [Deployment.md](../operations/Deployment.md#7-nginx)). Поэтому код, конфиги и документы наружу не отдаются — на любой незнакомый путь роутер отвечает JSON-ошибкой.
2. **Обработчики ошибок.** `index.php` выключает `display_errors` и ставит:
   - `set_exception_handler` — любое необработанное исключение пишется в лог (`error_log`), клиент получает HTTP 500 и `errorCode` 9001 (`INTERNAL_ERROR`). Детали ошибки наружу не уходят;
   - `register_shutdown_function` — то же для фатальных ошибок (`E_ERROR`, `E_PARSE`, …), которые исключением не ловятся, например нехватка памяти.
3. **Маршрутизация.** Путь без query string ищется в массиве `$routes` точным совпадением (с учётом регистра). Не найден — HTTP 404 и `errorCode` 404. Найден — файл обработчика подключается через `require`. HTTP-метод роутер не проверяет: обработчик POST-метода читает параметры из `$_POST`, и при GET-запросе просто не найдёт их (ошибка валидации).
4. **Обработчик** — плоский скрипт без классов и функций, шаги всегда в одном порядке:
   1. `require_once` нужных классов из `core/`;
   2. авторизация — `Auth::requireUserId()` (или `Admin::require()` в админке): без сессии ответ `2003` и выход;
   3. разбор и проверка параметров: ошибка — `Response::error(ErrorCode::…)`;
   4. работа с данными через сущности `core/` (транзакции и блокировки — внутри сущностей);
   5. после коммита — публикация WS-событий (`WebSocket::publish*`);
   6. `Response::success($data, $actions)`.
5. **Ответ.** `Response::success()` и `Response::error()` пишут JSON и вызывают `exit` — это и есть управление потоком: после `Response::error()` код обработчика не выполняется, проверки идут подряд без `else`.

Пример — `messages/send.php`: `Auth::requireUserId()` → проверка членства (`5002`), текста (`1005`), `clientId` (`1006`) → `Message::send()` в транзакции → `Message::publishReceived()` → ответ с `message`, `readInfo` и action `users`.

## Общий код (`core/`)

Инфраструктура:

| Класс | Назначение |
|-------|------------|
| `Response` | `success(data, actions)` → `{"status":1,"response":{…},"actions":[…]}`, `error(code)` → `{"status":0,"errorCode":…}`; JSON без экранирования юникода и слешей, невалидный UTF-8 заменяется на U+FFFD. Пустой `response` сериализуется как `{}`, пустые и `null`-actions отбрасываются |
| `ErrorCode` | Константы кодов ошибок, сгруппированы по тысячам (1xxx — валидация, 2xxx — авторизация, 3xxx — файлы, …). Описания — [Errors.md](../api/Errors.md) |
| `Request` | Разбор общих параметров: `requireIdList()` (списки id для `getBatch`: `ids=1,2` или `ids[]=1&ids[]=2`, без повторов, с лимитом), `optionalUint()` (необязательное неотрицательное целое) |
| `Action` | Сборка [actions](../api/General.md#actions) ответа. Сейчас один тип — `users` |
| `DB` | Одно PDO-соединение на процесс (`DB::get()`): исключения на ошибках, настоящие prepared statements, `time_zone = '+00:00'`. Хелперы времени `ms()` / `fromMs()`, `reset()` и `isConnectionLost()` для долгоживущего WS-сервера |
| `Session` | Старт и продление PHP-сессии — [Sessions.md](Sessions.md) |
| `Auth` | `requireUserId()` / `currentUserId()` — пользователь текущей сессии |
| `Admin` | Вход и проверка доступа админ-панели |
| `WebSocket` | Сторона API для WS: токены подключения и вызовы WS-сервера (`publish`, `publishEach`, `endSession`) — [WebSocket.md](WebSocket.md) |

Сущности — статические методы над таблицами, наружу отдают массивы в формате API:

| Класс | Таблицы | Что умеет |
|-------|---------|-----------|
| `User` | `users` (+ `files` для аватара) | Поиск по id, списку id, подстроке |
| `File` | `files` | Сохранение изображения с уменьшенной копией, поиск — [Files.md](Files.md) |
| `Conversation` | `conversations`, `conversation_members` | Личные переписки, списки и синхронизация, прочтение, версии пользователя |
| `Message` | `messages`, `message_blocks` | Отправка, правка, выборка блоками, синхронизация кэша |

Правила сущностей:

- **`fromRow()`** — единственное место, где `snake_case` из БД превращается в `lowerCamelCase` API; связанные объекты (аватар, последнее сообщение) выбираются одним запросом через `JOIN` с префиксами колонок (`f_`, `lm_`) и собираются вложенными `fromRow()`.
- **Время** выбирается сразу в миллисекундах — `DB::ms('created_at')`, параметры-миллисекунды сравниваются через `DB::fromMs()`.
- **Объекты зависят от смотрящего.** `Conversation` собирается для конкретного пользователя (`$viewerId`): `opponentUserId`, `unreadCount`, `lastReadMessageId`, `changeVersion` у каждого участника свои. Поэтому WS-события с перепиской рассылаются отдельной доставкой каждому участнику.
- **Транзакции открывают сущности**, а не обработчики (`Message::send()`, `Message::edit()`, `Conversation::markRead()`, `Conversation::findOrCreateSingle()`). Исключение — `conversations/getList.php`: список и общий счётчик читаются в одной транзакции `REPEATABLE READ`, чтобы быть из одного снимка. Порядок блокировок — в [DataModel.md](DataModel.md#транзакции-и-блокировки).
- **Результаты изменения возвращаются через ссылочные параметры** (`&$isNew`, `&$created`, `&$readInfos`, `&$changeVersions`) — обработчику они нужны, чтобы решить, какие события и кому рассылать.

## WebSocket-события из API

API не держит соединений: после коммита он синхронно вызывает внутренний HTTP-эндпоинт WS-сервера (`127.0.0.1:WEBSOCKET_INTERNAL_PORT`) с таймаутом 200 мс. Ошибка вызова только логируется — REST-ответ не ломается, клиент досинхронизируется через REST при переподключении. Какие методы какие события публикуют — [WebSocket.md](WebSocket.md#события-и-источники), контракт событий — [docs/api/WebSocket.md](../api/WebSocket.md).

## Конфигурация

Настройки — PHP-константы (`define`), подключаются через `require_once` там, где нужны. `config/local.php` задаёт `LOCAL_CONFIG_DIR` — каталог с локальными `db.php` и `app.php`; по умолчанию `config/`, тесты подставляют `tests/config/` через переменную окружения `SERVERAI_CONFIG_DIR`. Полный список настроек — [Configuration.md](../operations/Configuration.md).

## Админ-панель

`admin/index.php` отдаёт одну HTML-страницу со встроенными стилями и JS, без сборки и внешних библиотек. Вся логика — в JS, который вызывает JSON-методы `/admin/*` (поиск пользователя → его переписки → отправка сообщения или отметка прочтения от его имени). Методы админки переиспользуют сущности и рассылку событий клиентских методов (`Message::send()` + `Message::publishReceived()`, `Conversation::markRead()` + `Conversation::publishRead()`), поэтому для клиентов действие из админки неотличимо от действия самого пользователя. Доступ — отдельная сессия, см. [Sessions.md](Sessions.md#админ-панель).
