# WebSocket: серверная архитектура

[← Обзор архитектуры](Overview.md)

Документ описывает, как устроена серверная сторона WebSocket. Клиентский контракт (методы `/global/start` и `/global/getWebsocketToken`, формат сообщений, коды закрытия) — в [api/WebSocket.md](../api/WebSocket.md).

## Компоненты

```
 Клиент ──HTTP──▶ PHP API (index.php)
   │                 │  1. /global/start, /global/getWebsocketToken: выдаёт токен (таблица websocket_tokens)
   │                 │  3. события (messages/send, edit, logout …) ──▶ publish
   │                 ▼
   └──WS──▶ WebSocket-сервер (отдельный долгоживущий процесс)
              2. auth/connect: гасит токен в БД, привязывает соединение к user_id + session_id
              4. рассылает события в соединения пользователя
```

- **PHP API** — существующий код. Выдаёт токены и сообщает WS-серверу о событиях.
- **WebSocket-сервер** — отдельный процесс `websocket/server.php` (CLI), запускается рядом с API. Держит соединения, проверяет токены, рассылает события. Использует общий код `core/` (`DB`, `WebSocket`).
- **Внутренний канал publish** — по нему API передаёт WS-серверу события и команды закрытия.

Файлы:

| Файл                                   | Что внутри                                                                 |
|----------------------------------------|----------------------------------------------------------------------------|
| `core/WebSocket.php`                   | Сторона API: `issueToken`, `consumeToken`, `endSession`, `publish`, `publishEach`, `delivery`, `message` |
| `global/start.php`, `global/getWebsocketToken.php` | Выдача `WebsocketConnectInfo`                                   |
| `websocket/server.php`                 | Точка входа процесса: читает конфиг и опции, запускает `WsServer`           |
| `websocket/WsServer.php`               | Цикл `stream_select()`, соединения клиентов, внутренний HTTP, таймеры        |
| `websocket/WsFrame.php`                | Фреймы RFC 6455: сборка, разбор, ключ handshake                             |
| `websocket/WsMessage.php`              | Конверт сообщений протокола: разбор сообщений клиента, сборка событий, UUID  |
| `config/websocket.php`                 | Таймауты и лимиты (в репозитории)                                           |

Запуск: `php websocket/server.php`. В продакшене — под supervisor/systemd с автоперезапуском; остановка по `SIGTERM` (или `SIGINT`) закрывает соединения с кодом `1001`, и клиенты переподключаются. Пока WS-сервер не запущен, REST работает как обычно — вызовы publish только пишут ошибку в лог.

## WebSocket-сервер

**Чистый PHP без зависимостей** (как и весь проект): один процесс, цикл на `stream_select()` с шагом 0,25 с, своя реализация RFC 6455 — handshake, фреймы text/ping/pong/close, маскирование, фрагментация. Некорректный handshake получает HTTP 400. Сокеты неблокирующие, исходящие данные копятся в буфере соединения и отправляются, когда сокет готов к записи.

Состояние процесса (в памяти):

- `clients[id сокета]` — `WsConnection`: буферы, состояние (`handshake` / `pending` / `authorized`), `userId`, `sessionId`, время последнего фрейма, неподтверждённые события;
- индексы `byUser[user_id]` и `bySession[session_id]` — только авторизованные соединения, которым ещё не отправлен close.

Таймеры в цикле:

- неавторизованные соединения закрываются через `WEBSOCKET_AUTH_TIMEOUT` (10 с) без `auth` / `connect` — с кодом `4002` (без handshake — просто разрыв TCP);
- соединения, от которых `WEBSOCKET_IDLE_TIMEOUT` (60 с) не приходило ни одного фрейма, разрываются без close-фрейма (у клиента — `1006`). Heartbeat инициирует клиент ping-фреймами раз в 25 с; сервер отвечает pong и сам ping не шлёт;
- после отправки close сервер ждёт ответный close не дольше 2 с, затем разрывает TCP.

Лимиты:

- сверх `WEBSOCKET_MAX_CONNECTIONS` (1000) клиентских соединений новые закрываются сразу после accept, до handshake (у клиента — ошибка подключения, он переподключается с задержкой); внутренних соединений от API — не больше 16;
- если неотправленные данные соединения превысили `WEBSOCKET_MAX_OUTPUT_BUFFER` (1 МБ) — клиент не читает сокет, а события копятся, — соединение разрывается без close-фрейма (у клиента — `1006`). Без лимита такой клиент, продолжая слать ping, раздувал бы память процесса до `memory_limit`.

В продакшене WS-сервер стоит за nginx (TLS, `wss://`, проксирование `Upgrade`); `url` в `WebsocketConnectInfo` указывает на внешний адрес. В nginx `proxy_read_timeout` должен быть больше интервала клиентских ping (например, 75 с).

### Известные ограничения

- **Потолок соединений.** `stream_select()` построен на `select()`, ограниченном `FD_SETSIZE` (обычно 1024 дескриптора на процесс). С дескриптором за этим пределом `stream_select()` перестаёт работать целиком, поэтому число соединений ограничено `WEBSOCKET_MAX_CONNECTIONS` (1000) с запасом под слушающие сокеты, внутренние соединения, stdio и соединение с БД. Дальше — Workerman/Swoole (event-loop на `epoll`) или отдельный сервис на Go/Node; протокол и канал publish от выбора не зависят. При нескольких процессах канал publish заменяется на Redis pub/sub — интерфейс `core/WebSocket.php` при этом не меняется.
- **Блокирующие запросы к БД.** Процесс однопоточный: запрос к MySQL при `auth` / `connect` блокирует обработку всех соединений на время запроса. Для MySQL на localhost это единицы миллисекунд — приемлемо. Кроме проверки токена WS-сервер в БД не ходит; данные событий приходят готовыми через publish.
- **Обрыв соединения с MySQL.** Долгоживущее соединение MySQL закрывает после `wait_timeout` простоя (по умолчанию 8 часов) — следующий запрос падает с «MySQL server has gone away». WS-сервер при такой ошибке (`2006` / `2013`, `DB::isConnectionLost()`) сбрасывает соединение `DB::reset()` и повторяет запрос один раз; если не вышло — клиент получает `connectionError` с `9001`.

## Токены подключения

Хранятся в БД — их выдаёт PHP API, а проверяет WS-сервер. Таблица — единственный источник правды о том, можно ли подключиться: WS-сервер не читает PHP-сессии.

Миграция `db/008_websocket_tokens.sql` (`007` — `conversations.updated_at`):

```sql
CREATE TABLE websocket_tokens (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    token_hash  CHAR(64)     NOT NULL,          -- sha256(token), сам токен не храним
    user_id     INT UNSIGNED NOT NULL,
    session_id  VARCHAR(128) NOT NULL,          -- id PHP-сессии, для которой выдан
    expires_at  TIMESTAMP    NOT NULL,
    created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY token_hash (token_hash),
    KEY session_id (session_id),
    KEY expires_at (expires_at),
    CONSTRAINT websocket_tokens_user_fk FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- **Выдача** (`/global/start`, `/global/getWebsocketToken`): `bin2hex(random_bytes(32))` — 64 hex-символа; в БД — `hash('sha256', token)`, `expires_at = now + WEBSOCKET_TOKEN_TTL`. Клиенту отдаётся `expiresIn = WEBSOCKET_TOKEN_TTL` — относительное время, не зависящее от часов устройства. Попутно удаляются истёкшие записи (`DELETE … WHERE expires_at < NOW()`), отдельный крон не нужен. Ответ — с заголовком `Cache-Control: no-store` (выставляется в самих методах через `header()`), чтобы токен не осел в HTTP-кэше клиента или прокси.
- **Проверка** (`auth` / `connect` на WS-сервере, `WebSocket::consumeToken()`): `SELECT` по `token_hash`, затем `DELETE` записи — токен гасится при любой попытке. Токен засчитывается, только если `DELETE` удалил запись (`rowCount() = 1`): из двух параллельных попыток с одним токеном успешна не больше одной. Ошибка `2004`, если запись не найдена, `expires_at <= NOW()` или `user_id` не совпадает с `userId` из `body`. При ошибке сервер отправляет `auth` / `connectionError` и закрывает соединение с кодом `4001`. Невалидные параметры (`1004`) токен не гасят — его нельзя найти без `token`.
- **Отзыв**: при `/auth/logout`, а также при `/auth/login` и `/auth/signup` (они делают `session_regenerate_id(true)`, старая сессия уничтожается) удаляются токены старого `session_id`; при удалении пользователя — каскадом. Отозванный токен при подключении даёт `2004`, поэтому живость сессии на WS-сервере отдельно не проверяется.

Почему одноразовый короткий токен, а не cookie сессии: WS-сервер не должен разбирать cookie и PHP-сессии, токен не даёт доступа к REST API и при утечке (логи, прокси) бесполезен через 2 минуты или после первого использования. Аутентификация не через cookie также снимает cross-site WebSocket hijacking — проверка `Origin` не нужна.

### Лёгкий метод для переподключений

`/global/start` со временем будет расширяться (конфиг, флаги, счётчики) и не должен вызываться на каждое переподключение: при массовом обрыве (перезапуск WS-сервера, `1001`) все клиенты пришли бы в него одновременно. Поэтому для переподключений есть отдельный `/global/getWebsocketToken`: проверка сессии + одна вставка в `websocket_tokens`, больше ничего. Общая логика выдачи токена — в `core/WebSocket.php` (`issueToken(int $userId, string $sessionId): array`), оба метода её переиспользуют. `/global/start` для анонима без cookie сессию не стартует (`Auth::currentUserId()`), чтобы не плодить пустые сессии.

## Канал publish (API → WS-сервер)

WS-сервер слушает внутренний HTTP-эндпоинт только на `127.0.0.1` (отдельный порт), запросы подписаны общим секретом из конфига (`WEBSOCKET_INTERNAL_SECRET`, заголовок `X-Internal-Secret`).

`POST /publish`, JSON — список доставок, у каждой свои получатели и своё сообщение:

```json
{
  "deliveries": [
    {
      "recipientIds": [1],
      "message": { "group": "...", "event": "...", "body": { }, "userIds": [1, 2] }
    }
  ]
}
```

WS-сервер генерирует `uid` для каждого отправляемого сообщения и рассылает его во все авторизованные соединения получателей. `userIds` в сообщении — поле протокола для клиента (пользователи, фигурирующие в событии), не путать с `recipientIds`.

Несколько доставок в одном запросе нужны, когда содержимое события зависит от получателя: [Conversation](../api/Objects.md#объект-conversation) содержит `opponentUserId` относительно текущего пользователя, поэтому `conversations` / `singleCreated` строится отдельно для каждого участника. События, одинаковые для всех (`messages` / `received`, `messages` / `edited`), идут одной доставкой со всеми участниками в `recipientIds`. `body` событий содержит полные объекты сущностей с `updatedAt` — клиент применяет их идемпотентно (см. [Синхронизация](../api/WebSocket.md#синхронизация)); без этого событие в протокол не добавляется. Исключение — переписка в событиях `messages`: они несут только её `lastMessage` (позиция — `message.createdAt`), версионированные парой `(positionUpdatedAt, messageId)` и `lastMessage.updatedAt` (см. [Слияние переписки](../api/WebSocket.md#слияние-переписки) и [ConversationList.md](ConversationList.md)).

`POST /closeSession` — `{ "sessionId": "...", "code": 4003 }`: закрыть все соединения сессии (код — от 4000 до 4999).

Ответ — `200 {"status":1}`; невалидное тело — `400`, неверный секрет — `403`, неизвестный путь — `404`. Доставки `/publish` сначала проверяются все, поэтому невалидный запрос не рассылается частично.

На стороне API — `core/WebSocket.php`:

- `publish(array $recipientIds, string $group, string $event, array $body, array $userIds = [])` — одно событие всем получателям;
- `publishEach(array $deliveries)` + `delivery(...)` — несколько доставок одним запросом;
- `endSession(string $sessionId)` — удаляет токены сессии и вызывает `/closeSession` с `4003`. Вызывается из `/auth/logout`, а также из `/auth/login` и `/auth/signup`, если старая сессия была авторизована.

**Таймауты.** Вызовы `publish` и `closeSession` синхронные и не должны заметно замедлять REST-запрос: таймаут подключения — 50 мс, ожидание ответа — 200 мс (`WEBSOCKET_INTERNAL_CONNECT_TIMEOUT`, `WEBSOCKET_INTERNAL_TIMEOUT`; WS-сервер только кладёт сообщение в буферы соединений и сразу отвечает). Вызов — после коммита транзакции. Ошибка или таймаут логируются и **не** роняют REST-запрос: доставка не гарантирована, клиент синхронизируется через REST при переподключении. Для `closeSession` неудача безопасна: токены сессии уже удалены, а REST-методы отвечают `2003`, так что недозакрытое соединение лишь получает события до своего обрыва.

## Подтверждения получения

На каждое событие сервера, кроме группы `auth`, клиент отвечает `events` / `received` с `receivedUid`. Сейчас подтверждения используются только для мониторинга: WS-сервер держит в памяти соединения отправленные неподтверждённые `uid` (не больше `WEBSOCKET_MAX_UNACKED` = 1000 на соединение — старые вытесняются) и при подтверждении удаляет `uid` из набора. Каждое отправленное сообщение получает свой `uid`, даже если это одно событие в нескольких соединениях. Подтверждение с `uid`, которого нет в наборе соединения, игнорируется. Неподтверждённые за `WEBSOCKET_ACK_TIMEOUT` (30 с) события пишутся в лог WS-сервера. Повторной отправки нет. При закрытии соединения набор сбрасывается.

Если понадобится гарантированная доставка, на эту же схему ложится очередь событий на пользователя с повторной отправкой неподтверждённых — протокол клиента менять не придётся.

## События и источники

| Событие                           | Где публикуется                 | Получатели               | `userIds`     |
|-----------------------------------|---------------------------------|--------------------------|---------------|
| `conversations` / `singleCreated` | `/conversations/createSingle`, только если переписка создана | Участники; отдельная доставка на каждого (своя `opponentUserId`) | `memberIds` |
| `messages` / `received`           | `/messages/send`                | Все участники переписки  | `[senderId]`  |
| `messages` / `edited`             | `/messages/edit`, только если текст изменился | Все участники переписки | `[senderId]` |
| `conversations` / `read`          | `/conversations/markRead`, если указатель сдвинулся | Прочитавший | — |
| `conversations` / `memberRead`    | Там же, одним `publishEach` с `read` | Остальные участники | `[userId]` |
| `groups` / `created`              | `/groups/create`                | Создатель                | `[создатель]` |
| `groups` / `membersAdded`         | `/groups/addMembers`, если кто-то добавлен | Добавленные — отдельная доставка на каждого (своя `changeVersion`); остальные участники — одна доставка с GroupInfo | `addedUserIds` |
| `groups` / `membersRemoved`       | `/groups/removeMembers`, если кто-то удалён | Удалённые — отдельная доставка на каждого (метка и счётчик); оставшиеся — одна доставка с GroupInfo | `removedUserIds` |
| `groups` / `memberLeft`           | `/groups/leave`                 | Вышедший (метка и счётчик); оставшиеся (GroupInfo) | вышедший и новый владелец |
| `groups` / `ownerChanged`         | `/groups/changeOwner`           | Все участники            | `[newOwnerUserId]` |

Признак создания переписки возвращает `Conversation::findOrCreateSingle($userId, $otherUserId, $created)` через третий параметр; участников переписки для `send` / `edit` — `Conversation::findMemberIds()`. События групп собирают `Group::publish*()` из результата изменения — тела и версии сняты в транзакции изменения ([Groups.md](Groups.md#websocket-группа-groups)).

## Конфигурация

Локальные настройки — в `config/app.php` (шаблон `config/app.example.php`):

```php
define('WEBSOCKET_URL', 'ws://localhost:8081');          // внешний адрес, отдаётся клиенту
define('WEBSOCKET_LISTEN', 'tcp://0.0.0.0:8081');        // где WS-сервер принимает клиентов
define('WEBSOCKET_INTERNAL_PORT', 8082);                 // внутренний эндпоинт, только 127.0.0.1
define('WEBSOCKET_INTERNAL_SECRET', '...');              // секрет API → WS-сервер
```

Для `config/app.php`, созданного до появления WebSocket, `WEBSOCKET_URL`, `WEBSOCKET_LISTEN` и `WEBSOCKET_INTERNAL_PORT` берут значения по умолчанию из шаблона (`config/websocket.php`). У `WEBSOCKET_INTERNAL_SECRET` умолчания нет: без него вызовы API → WS-сервер пропускаются с записью в лог (REST-методы работают, события не доставляются), а `websocket/server.php` не запускается.

Таймауты и лимиты — в `config/websocket.php` (в репозитории): `WEBSOCKET_TOKEN_TTL` (120 с), `WEBSOCKET_AUTH_TIMEOUT` (10 с), `WEBSOCKET_IDLE_TIMEOUT` (60 с), `WEBSOCKET_MAX_MESSAGE_SIZE` (64 КБ), `WEBSOCKET_ACK_TIMEOUT` (30 с), `WEBSOCKET_MAX_UNACKED` (1000), `WEBSOCKET_INTERNAL_CONNECT_TIMEOUT` (50 мс), `WEBSOCKET_INTERNAL_TIMEOUT` (200 мс), `WEBSOCKET_MAX_CONNECTIONS` (1000), `WEBSOCKET_MAX_OUTPUT_BUFFER` (1 МБ). Таймауты авторизации и тишины и оба лимита можно переопределить опциями `--auth-timeout` / `--idle-timeout` / `--max-connections` / `--max-output-buffer` (их использует раннер тестов).

## Сценарии

**Подключение.** `/global/start` (или `/global/getWebsocketToken` при переподключении) → токен в БД → клиент открывает WS → `auth` / `connect` → токен гасится и проверяется → соединение в индексах → `auth` / `connected` (при ошибке — `auth` / `connectionError` 2004 и закрытие `4001`) → клиент синхронизируется через REST.

**Событие.** Например, `/messages/send`: сообщение сохранено → `WebSocket::publish(memberIds, 'messages', 'received', ['message' => полный Message], [senderId])` → WS-сервер рассылает по соединениям участников (включая все соединения отправителя) → клиенты отвечают `events` / `received`.

**Выход.** `/auth/logout` → `WebSocket::endSession(sessionId)`: удаляются токены сессии, вызывается `/closeSession` → соединения сессии закрываются с `4003`. Соединения других сессий пользователя не трогаются.

**Повторный вход.** `/auth/login` в той же сессии → токены старой сессии удаляются, соединения старой сессии закрываются с `4003`. Клиент к этому моменту уже вызвал `/global/start`, открыл новое соединение и игнорирует закрытие старого (правило [текущего соединения](../api/WebSocket.md#текущее-соединение)).

**Удаление пользователя.** Токены удаляются каскадом; соединения нужно будет закрывать через `/closeSession` по сессиям пользователя (или отдельным `closeUser`), когда появится метод удаления.

**Перезапуск WS-сервера.** Все соединения закрываются с `1001`, клиенты переподключаются через `/global/getWebsocketToken` с экспоненциальной задержкой и разбросом. Состояние в памяти восстанавливать не нужно.

## Открытые вопросы

- Ответы сервера на запросы клиента через WS. Сейчас клиент шлёт только `auth` / `connect` и `events` / `received`; если появятся запросы, предлагается добавить в `body` ответа поле `requestUid` с `uid` исходного сообщения.
- Нужна ли гарантированная доставка событий (повторная отправка неподтверждённых, докачка пропущенного при переподключении) или достаточно REST-синхронизации. Подтверждения `events` / `received` для неё уже есть.
- Ограничение числа одновременных соединений на пользователя.
- Версия клиента в `auth` / `connect` (`platform`, `appVersion`), ограничение частоты подключений и вызовов `/global/*`, ограничение числа попыток при `1009` / `4000`.
