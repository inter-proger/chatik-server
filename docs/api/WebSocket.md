# WebSocket

[← Документация API](README.md)

WebSocket-соединение — канал, по которому сервер в реальном времени присылает клиенту события (новые сообщения, изменения и т. п.). Канал не гарантирует доставку: события, произошедшие, пока соединения не было, повторно не присылаются. Поэтому после каждого успешного (пере)подключения клиент синхронизирует актуальное состояние через REST-методы (см. [Синхронизация](#синхронизация)), а WebSocket использует только для обновлений «с этого момента».

## Подключение

1. Клиент получает [WebsocketConnectInfo](Objects.md#объект-websocketconnectinfo):
   - при старте, после входа/выхода и при возврате из фона — из [`/global/start`](methods/Global.md#get-globalstart--старт-работы-приложения). Если `websocketConnectInfo` равен `null` — пользователь не авторизован, подключаться не нужно (а открытое соединение нужно закрыть);
   - при переподключении — из [`/global/getWebsocketToken`](methods/Global.md#get-globalgetwebsockettoken--токен-подключения-к-websocket). Ошибка `2003` — пользователь не авторизован, переподключаться не нужно.
2. Клиент открывает WebSocket-соединение по адресу `url` (без дополнительных параметров и заголовков). На некорректный запрос handshake сервер отвечает HTTP 400.
3. Первым сообщением клиент отправляет [`auth` / `connect`](websocket/Auth.md#auth--connect--авторизация-соединения) с `userId` и `token`. Если оно не пришло в течение 10 секунд, сервер закрывает соединение с кодом `4002`.
4. Сервер отвечает [`auth` / `connected`](websocket/Auth.md#auth--connected--соединение-авторизовано) — соединение готово — либо [`auth` / `connectionError`](websocket/Auth.md#auth--connectionerror--ошибка-авторизации) и закрывает соединение. До `connected` сервер событий не присылает.
5. Клиент синхронизирует состояние через REST-методы.

Токен одноразовый и короткоживущий, поэтому **перед каждым подключением, включая переподключение, клиент получает новый токен**.

У одного пользователя может быть несколько одновременных соединений (несколько устройств или сессий); события пользователя рассылаются во все его соединения.

## Текущее соединение

В каждый момент у клиента не больше одного **текущего** соединения. Открывая новое соединение, клиент закрывает предыдущее (код `1000`) и с этого момента считает текущим новое.

Клиент обрабатывает события и закрытие **только текущего** соединения. Закрытие соединения, которое клиент сам закрыл или заменил новым, игнорируется — по нему не переподключаются и не меняют состояние авторизации. Пример: после входа под другим пользователем сервер закрывает соединения старой сессии с кодом `4003`, но клиент к этому моменту уже закрыл старое соединение и открыл новое — `4003` по старому соединению ничего не меняет.

## Синхронизация

Порядок: сначала `auth` / `connected`, затем REST-запросы. Так события, произошедшие во время синхронизации, не теряются — но могут прийти раньше ответа REST и оказаться новее его данных. Поэтому:

- событие несёт **версию изменения** и позволяет применить его **идемпотентно и независимо от порядка доставки**: повторное применение ничего не меняет, а более старая версия, пришедшая позже, не откатывает более новую;
- клиент применяет события и данные REST по одним правилам слияния — по версии объекта.

Это обязательное требование к будущим событиям. Допустимые формы события:

1. **Полный объект или его независимо версионируемая часть** — клиент сливает по версии: [Message](Objects.md#объект-message) — по `updatedAt` (побеждает больший, при равенстве — любой), [GroupInfo](Objects.md#объект-groupinfo) — по `version`, [ReadInfo](Objects.md#объект-readinfo) — по `changeVersion`, части [Conversation](Objects.md#объект-conversation) в событиях [`messages`](websocket/Messages.md) — по [правилам слияния переписки](#слияние-переписки).
2. **Ссылка и версия** — клиент перезапрашивает объект по REST. Версия такого события считается увиденной (попадает в [курсор](#курсор-синхронизации)) только после успешного ответа REST; пока запрос не удался, клиент хранит ссылку и повторяет запрос после каждого переподключения. Пример — [`groups` / `membersAdded`](websocket/Groups.md#groups--membersadded--участники-добавлены) для добавленного.

Дельта без версии («добавлен X») недопустима: два таких события, пришедшие в обратном порядке, дали бы неверный результат. Исключение — значения, которые только растут и сливаются по максимуму: указатель прочтения в [`conversations` / `memberRead`](websocket/Conversations.md#conversations--memberread--участник-прочитал-переписку) (см. [MemberReadMeta](Objects.md#объект-memberreadmeta)).

У каждой сущности, которую меняет событие, есть **путь восстановления** после потерянного события — одно из двух:

- **синхронизация по курсору** — изменение поднимает версию пользователя, и [`getList`](methods/Conversations.md#синхронизация-списка) с `changedAfter` его вернёт: Conversation, ReadInfo, [RemovedConversation](Objects.md#объект-removedconversation);
- **перезапрос при открытии и после переподключения** — сущность нужна только на открытом экране: клиент запрашивает её при открытии и после каждого `auth` / `connected`, пока экран открыт; сохранённая копия закрытого экрана может устареть до следующего открытия: MemberReadMeta, GroupInfo.

Второе обязательное требование: любое новое изменяемое поле переписки, кроме позиции, увеличивает [версию](Objects.md#версия-пользователя) `changeVersion` участников (иначе фильтр `changedAfter` его потеряет), а событие этого изменения несёт новую версию получателя (иначе [курсор синхронизации](#курсор-синхронизации) остановится на ней до переподключения). Указатели прочтения других участников и состав группы в Conversation не входят, поэтому версию не поднимают: `memberRead` и события [GroupInfo](Objects.md#объект-groupinfo) остальным участникам группы не несут `changeVersion` и курсор не двигают.

### Слияние переписки

У [Conversation](Objects.md#объект-conversation) три независимые версии: позиция в списке (`positionUpdatedAt` вместе с `lastMessage`), информация (`updatedInfoAt`) и прочтение (`changeVersion`). Правило «побеждает больший `updatedAt`» к ней не применяется. Вместо него клиент применяет по порядку четыре правила к каждой пришедшей версии переписки — из [`getList`](methods/Conversations.md#get-conversationsgetlist--список-переписок), [`getBatch`](methods/Conversations.md#get-conversationsgetbatch--переписки-по-списку-id), [`createSingle`](methods/Conversations.md#post-conversationscreatesingle--создание-личной-переписки), события [`conversations` / `singleCreated`](websocket/Conversations.md#conversations--singlecreated--создана-личная-переписка), ответа [`/groups/create`](methods/Groups.md#post-groupscreate--создание-группы), события [`groups` / `created`](websocket/Groups.md#groups--created--группа-создана) и событий [`messages` / `received` и `edited`](websocket/Messages.md) (у них `positionUpdatedAt` = `message.createdAt`):

1. **Позиция.** Версия позиции — пара `(positionUpdatedAt, lastMessage.messageId)`, сравнивается лексикографически; у `lastMessage: null` — `messageId = 0`. Если пришедшая пара **строго больше** локальной — взять `positionUpdatedAt` и `lastMessage` целиком и переместить переписку по сортировке. `messageId` в паре нужен для сообщений, отправленных в одну миллисекунду: id сообщений внутри переписки растут строго.
2. **Текст последнего сообщения.** Если после шага 1 `lastMessage.messageId` пришедшей версии совпадает с локальным, а `lastMessage.updatedAt` больше локального — взять `lastMessage`. Так правка применяется только к тому же сообщению и не откатывается более старой правкой.
3. **Информация.** Только для полного объекта Conversation (ответы REST, `singleCreated`, `groups` / `created`): если `updatedInfoAt` больше локального — взять `memberIds`, `name`, `description`, `avatar`, `opponentUserId`, `updatedInfoAt`. События `messages` `updatedInfoAt` не меняют: иначе локальная версия «обогнала» бы не пришедшие изменения названия или участников, и следующий ответ REST с тем же `updatedInfoAt` их бы не применил.
4. **Прочтение.** Для полного объекта Conversation и для [ReadInfo](Objects.md#объект-readinfo) (ответы `markRead` и `/messages/send`, события `conversations` / `read` и `messages` / `received`): если пришедший `changeVersion` больше локального — взять `unreadCount`, `lastReadMessageId`, `changeVersion`. Информацию по `changeVersion` не сливают: события `messages` несут версию, но не информацию, и применённая из события версия отбросила бы ещё не пришедшие изменения информации. Версия переписки растёт и при изменении информации — тогда поля прочтения приходят те же, и их повторное применение безвредно. Общий счётчик `totalUnreadCount` сливается отдельно, по своей локальной версии (см. [ReadInfo](Objects.md#объект-readinfo)).

При повторе той же версии ни одно правило не срабатывает.

Порядок доставки `received` и `edited` между собой не гарантирован; правила покрывают оба случая. Если `edited` по сообщению M15 пришло после `received` по более новому M16 — позиция события меньше локальной, `messageId` не совпадает, превью не откатывается. Если `edited` по M16 пришло раньше `received` по M16 — переписка поднимается сразу с отредактированным текстом, а последующее `received` (равная позиция, меньший `lastMessage.updatedAt`) ничего не меняет.

### Курсор синхронизации

Клиент хранит `syncedChangeVersion` — [версию пользователя](Objects.md#версия-пользователя), до которой он видел все изменения, — и множество `seenVersions`: версии выше курсора, пришедшие в событиях. Курсор — значение фильтра `changedAfter` при [синхронизации списка](methods/Conversations.md#синхронизация-списка).

Каждое изменение увеличивает версию пользователя ровно на 1 и доставляется во все его соединения событием с версией этого изменения:

| Изменение | Событие | Версия |
|-----------|---------|--------|
| Прочтение (`markRead`) | [`conversations` / `read`](websocket/Conversations.md#conversations--read--переписка-прочитана) | `readInfo.changeVersion` |
| Новое сообщение | [`messages` / `received`](websocket/Messages.md#messages--received--новое-сообщение) | `readInfo.changeVersion` |
| Правка последнего сообщения | [`messages` / `edited`](websocket/Messages.md#messages--edited--сообщение-отредактировано) | `changeVersion` |
| Создание личной переписки | [`conversations` / `singleCreated`](websocket/Conversations.md#conversations--singlecreated--создана-личная-переписка) | `conversation.changeVersion` |
| Создание группы | [`groups` / `created`](websocket/Groups.md#groups--created--группа-создана) | `conversation.changeVersion` |
| Добавление в группу | [`groups` / `membersAdded`](websocket/Groups.md#groups--membersadded--участники-добавлены) — добавленному | `changeVersion`, после успешного `getBatch` |
| Удаление из группы, выход | [`groups` / `membersRemoved`](websocket/Groups.md#groups--membersremoved--участники-удалены), [`memberLeft`](websocket/Groups.md#groups--memberleft--участник-вышел) — удалённому, вышедшему | `removedConversation.changeVersion` |

**Правило непрерывности.** Событие с версией `v` всегда применяется по правилам слияния. Если `v > syncedChangeVersion`, `v` добавляется в `seenVersions`. Затем, пока `syncedChangeVersion + 1` есть в `seenVersions`, курсор растёт на 1, а версия убирается из множества. События, пришедшие во время синхронизации, обрабатываются так же; после последней страницы `changedAfter` курсор встаёт на версию ответа, версии не выше него убираются из `seenVersions`, и курсор снова продвигается по правилу.

Курсор не перескакивает версию, событие которой не дошло: доставка по WebSocket не гарантирована, а события параллельных запросов могут прийти не в порядке версий. Пропуск остаётся до следующей синхронизации — `changedAfter` с курсора вернёт пропущенное изменение (и уже полученные выше него: повторное слияние безвредно). Если разрыв держится дольше нескольких секунд, клиент может запустить синхронизацию `changedAfter`, не дожидаясь переподключения.

Ответы REST-методов (`markRead`, `/messages/send`) применяются слиянием, но курсор не двигают: то же изменение приходит событием во все соединения пользователя, включая вызвавшее.

Синхронизация списка переписок после переподключения — в описании [`/conversations/getList`](methods/Conversations.md#синхронизация-списка); синхронизация закэшированных сообщений переписки — в описании [`/messages/getList`](methods/Messages.md#синхронизация-кэша-сообщений).

## Формат сообщений

Все сообщения в обе стороны — текстовые фреймы с JSON-объектом:

| Поле      | Тип    | Обязательное | Описание                                                                          |
|-----------|--------|--------------|-----------------------------------------------------------------------------------|
| `uid`     | String | Да           | Уникальный идентификатор сообщения — UUID v4, генерирует отправитель               |
| `group`   | String | Да           | Группа событий (`auth`, `events`, `conversations`, `messages`, …)                  |
| `event`   | String | Да           | Событие внутри группы                                                              |
| `body`    | Object | Да           | Данные события; состав зависит от пары `group` + `event`. Если данных нет — пустой объект `{}` |
| `userIds` | Int[]  | Нет          | Только в событиях сервера: идентификаторы пользователей, фигурирующих в событии (участники переписки, отправитель сообщения и т. п.), без повторов, по возрастанию. Если таких пользователей нет — поле отсутствует. Клиент обрабатывает его так же, как [action `users`](General.md#action-users): недостающих в кэше (или устаревших) пользователей запрашивает через [`/users/getBatch`](methods/Users.md#get-usersgetbatch--пользователи-по-списку-id) пачками до 100. Событие может перечислять только пользователей, существенных для него: события [`groups`](websocket/Groups.md) — только затронутых изменением, а не всех участников из `groupInfo` |

```json
{
  "uid": "6f1c2a9e-4b7d-4e3a-9c51-0d2f8b6a7e14",
  "group": "auth",
  "event": "connected",
  "body": {}
}
```

Событие однозначно определяется парой `group` + `event`, далее записывается как `group` / `event`. Для каждого события описывается только содержимое `body`.

Правила:

- Клиент игнорирует события с неизвестными ему `group` или `event` (сервер будет добавлять новые).
- Сервер игнорирует неизвестные ему события от авторизованного клиента.
- Поле `userIds` в сообщениях клиента сервер игнорирует.
- Невалидный JSON, отсутствие любого из полей `uid`/`group`/`event`/`body` или неверный тип полей — ошибка протокола, сервер закрывает соединение с кодом `4000`.
- Максимальный размер сообщения от клиента — 64 КБ; при превышении сервер закрывает соединение с кодом `1009`.
- Бинарные фреймы не используются; полученный бинарный фрейм — ошибка протокола (`4000`).

## Подтверждение получения

На каждое событие сервера, **кроме группы `auth`**, клиент отвечает событием [`events` / `received`](websocket/Events.md#events--received--подтверждение-получения-события) с `uid` полученного события:

- подтверждение отправляется после того, как событие обработано (применено к локальному состоянию); загрузки пользователей по `userIds` ждать не нужно;
- события неизвестных клиенту `group` / `event` тоже подтверждаются — сразу, без обработки;
- подтверждение отправляется в то же соединение, из которого пришло событие; если соединение закрылось раньше, подтверждение не отправляется;
- на каждое событие — одно подтверждение; на повторно полученное событие с уже подтверждённым `uid` клиент отвечает повторно.

Сейчас сервер использует подтверждения для мониторинга доставки и неподтверждённые события повторно не отправляет — источником правды остаётся [синхронизация](#синхронизация) через REST. На подтверждения может опереться гарантированная доставка, если она появится.

## Поддержание соединения

Heartbeat инициирует **клиент**: каждые 25 секунд он отправляет protocol-level ping (фрейм ping по RFC 6455; на iOS — `URLSessionWebSocketTask.sendPing`, на Android — `pingInterval` в OkHttp). Сервер отвечает pong.

- Если pong не пришёл в течение 10 секунд, клиент считает соединение потерянным, закрывает его и переподключается.
- Если от клиента 60 секунд не приходило ни одного фрейма (ping, сообщения), сервер считает соединение мёртвым и разрывает его без close-фрейма — клиент увидит `1006`.
- Если клиент не успевает читать события и у сервера накопилось больше 1 МБ неотправленных данных соединения, сервер разрывает его без close-фрейма — клиент увидит `1006`.

Сервер сам ping не отправляет.

При уходе приложения в фон клиент закрывает соединение (код `1000`); при возврате из фона — вызывает `/global/start` и подключается заново.

## Коды закрытия соединения

Действия ниже относятся только к закрытию [текущего соединения](#текущее-соединение).

| Код  | Причина                                                                 | Действие клиента                                                   |
|------|-------------------------------------------------------------------------|--------------------------------------------------------------------|
| 1000 | Нормальное закрытие                                                     | Не переподключаться                                                 |
| 1001 | Сервер перезапускается / останавливается                                | Переподключиться с задержкой                                        |
| 1006 | Обрыв без кода (сеть, таймаут, переполнение буфера) — выставляется клиентской библиотекой | Переподключиться с задержкой                                        |
| 1009 | Слишком большое сообщение                                               | Ошибка клиента; переподключиться с задержкой                        |
| 1011 | Внутренняя ошибка сервера                                               | Переподключиться с задержкой                                        |
| 4000 | Ошибка протокола (невалидное сообщение, первое сообщение — не `auth` / `connect`, повторный `auth` / `connect`) | Ошибка клиента; переподключиться с задержкой |
| 4001 | Авторизация не удалась — перед закрытием сервер отправляет `auth` / `connectionError` | Действовать по `errorCode` из `connectionError`         |
| 4002 | Не получено `auth` / `connect` в течение 10 секунд                      | Переподключиться с задержкой                                        |
| 4003 | Сессия завершена (выход, повторный вход в той же сессии, удаление пользователя) | Не переподключаться автоматически; вызвать `/global/start` — если `websocketConnectInfo` равен `null`, перейти в неавторизованное состояние |

Переподключение — это получение токена через `/global/getWebsocketToken` и новое подключение. Задержка — экспоненциальная: 1, 2, 4, 8, 16, 30 секунд (дальше 30), со случайным разбросом ±20%; сбрасывается после успешного `auth` / `connected`. При появлении сети или возврате из фона клиент переподключается сразу, не дожидаясь задержки.
